# TCP 핸드셰이크와 keep-alive — 왜 세 번 인사하고 왜 끊지 않고 두는가

1일 1CS / 2주차 화요일 / 네트워크
티어: C (7섹션 전부)

---

## 한 줄 요약

3-way handshake는 **양쪽이 서로 보내고 받을 수 있음을 확인하는 최소 절차**이고,
keep-alive는 **그 비싼 절차를 매번 반복하지 않으려고 연결을 재사용하는 장치**입니다.

---

## 이게 없으면 생기는 문제

### 문제 1 — 상대가 살아 있는지 모르고 데이터를 보낸다

TCP는 "신뢰할 수 있는 전송"을 약속합니다. 보낸 게 도착하고, 순서가 지켜지고, 빠진 게 있으면 다시 보냅니다.
그런데 이 약속을 지키려면 **시작 시점에 두 가지를 확정**해야 합니다.

- 상대가 지금 이 포트에서 실제로 듣고 있는가
- 몇 번부터 순서를 세기 시작할 것인가 (시퀀스 번호)

이걸 확인하지 않고 그냥 보내면, 아무도 없는 곳에 데이터를 뿌리게 됩니다.
UDP가 정확히 이렇게 동작합니다. 빠르지만 도착 보장이 없습니다.

### 문제 2 — 매 요청마다 연결을 새로 맺으면 대기 시간이 요청 개수만큼 곱해진다

지난주 화요일에 본 요청의 여정에서, 데이터를 보내기 전에 이미 3번의 왕복이 있었습니다.
왕복 지연(RTT)이 50ms인 환경이라면:

```
연결 수립(3-way)      : 약 100ms   (1.5 RTT)
TLS 핸드셰이크(1.3)   : 약 50ms    (1 RTT)
실제 요청/응답        : 약 50ms
-----------------------------------
한 건에 약 200ms — 그중 실제 데이터는 50ms뿐
```

웹 페이지 하나가 API를 10번 호출한다면, 연결을 매번 새로 맺을 경우 **1.5초 중 1.25초가 인사말**입니다.
연결을 재사용하면 첫 번째만 200ms고 나머지 9번은 50ms씩입니다. 총 650ms.

같은 서버, 같은 코드인데 **연결 관리 방식만으로 2배 이상 차이**가 납니다.

### 문제 3 — 연결이 자원이라는 걸 모르면 고갈된다

연결 하나는 양쪽 모두에서 소켓 하나, 파일 디스크립터 하나, 커널 버퍼를 차지합니다.
재사용하지 않고 계속 새로 만들면 `Too many open files`가 뜨거나,
끊은 연결이 `TIME_WAIT` 상태로 쌓여 포트가 고갈됩니다.

---

## 비유

**전화 통화입니다.**

```
A: "여보세요?"          -> SYN     (내 말 들려요?)
B: "네, 들려요. 여보세요?" -> SYN+ACK (들려요. 제 말도 들려요?)
A: "네 들립니다."        -> ACK     (들려요)
--- 이제부터 본론 ---
```

왜 세 번인가가 여기서 자연스럽게 나옵니다.
두 번만 하면 **A가 B의 말을 들었다는 걸 B가 모릅니다.**
양방향을 확인하려면 각 방향마다 "보냄 + 확인"이 필요하고,
가운데 하나를 합칠 수 있어서 4번이 아니라 3번이 됩니다.

keep-alive는 **통화를 끊지 않고 두는 것**입니다.
할 말이 또 있는데 매번 끊고 다시 걸면, 신호 가는 시간이 통화 시간보다 길어집니다.

단, 이 비유가 놓치는 부분: 전화는 안 쓰면 그냥 조용하지만
TCP 연결은 **가만히 있어도 양쪽에서 메모리와 파일 디스크립터를 계속 점유합니다.**
그래서 무한정 열어둘 수 없고 타임아웃이 필요합니다.

---

## 실제로 어떻게 동작하는가

### 3-way handshake

```
클라이언트                                서버
    |                                      |
    |------- SYN (seq=x) ----------------->|   내 시작 번호는 x야
    |                                      |
    |<------ SYN+ACK (seq=y, ack=x+1) -----|   받았어. 내 시작 번호는 y야
    |                                      |
    |------- ACK (ack=y+1) --------------->|   받았어
    |                                      |
    |=========== 연결 수립됨 ==============|
```

핵심 목적 두 가지입니다.

- **양방향 통신 가능 확인** — 각 방향이 살아 있음을 서로 확인
- **시퀀스 번호 동기화** — 이 번호로 순서 보장과 재전송이 가능해짐

시퀀스 번호를 0이 아니라 임의의 값에서 시작하는 이유는 보안 때문입니다.
예측 가능하면 제3자가 연결에 끼어들 수 있습니다.

### 4-way handshake (종료)

수립은 3번인데 종료는 4번입니다.

```
클라이언트 --- FIN ----------> 서버      난 보낼 거 다 보냈어
클라이언트 <-- ACK ----------- 서버      알겠어
클라이언트 <-- FIN ----------- 서버      나도 다 보냈어
클라이언트 --- ACK ----------> 서버      알겠어
```

한쪽이 "다 보냈다"고 해도 **반대 방향은 아직 보낼 게 남았을 수 있습니다.**
그래서 각 방향을 따로 닫습니다. 합칠 수가 없어서 4번입니다.

마지막 ACK를 보낸 쪽은 `TIME_WAIT` 상태로 잠시(보통 60초) 남습니다.
마지막 ACK가 유실됐을 때 재전송에 응답하기 위해서입니다.
이게 쌓이면 포트 고갈의 원인이 됩니다.

### keep-alive — 이름이 같은 두 가지

**혼동하기 쉬운데 완전히 다른 개념 두 개가 같은 이름을 씁니다.**

| | HTTP keep-alive | TCP keep-alive |
|---|---|---|
| 계층 | 7계층 (응용) | 4계층 (전송) |
| 목적 | 연결 재사용으로 handshake 절약 | 죽은 연결 감지 |
| 동작 | 응답 후 연결을 끊지 않음 | 유휴 시 빈 패킷을 보내 생존 확인 |
| 설정 | `Connection: keep-alive` 헤더 | OS 소켓 옵션 |

대화에서 "keep-alive"라고 하면 보통 앞쪽입니다.
HTTP/1.1부터는 **기본값이 keep-alive**입니다. 끄려면 `Connection: close`를 명시해야 합니다.

### 커넥션 풀

keep-alive를 실제로 활용하는 구현체가 커넥션 풀입니다.
"연결을 미리 몇 개 만들어두고 돌려쓴다"가 전부입니다.

```python
# 권장 - httpx 클라이언트를 재사용한다 (연결 풀 유지)
import httpx

client = httpx.AsyncClient()      # 앱 시작 시 한 번만 생성

@app.get("/sensors")
async def get_sensors():
    resp = await client.get("https://external-api.com/data")
    return resp.json()
```

DB 연결도 같은 원리입니다. Django의 `CONN_MAX_AGE`가 이 설정입니다.

```python
# settings.py
DATABASES = {
    "default": {
        # ...
        "CONN_MAX_AGE": 60,   # 0이면 매 요청마다 연결을 새로 맺고 끊는다
    }
}
```

DB 연결 수립은 TCP handshake에 인증 절차까지 얹혀서 더 비쌉니다.
`CONN_MAX_AGE`가 0(기본값)이면 요청마다 이걸 반복합니다.

## 주니어가 자주 빠지는 함정

### 함정 1 — 요청마다 HTTP 클라이언트를 새로 만든다

```python
# 흔한 실수 - 매번 새 클라이언트 = 매번 새 연결 = 매번 handshake
@app.get("/sensors")
async def get_sensors():
    async with httpx.AsyncClient() as client:      # 여기서 연결 풀이 생겼다 사라짐
        resp = await client.get("https://external-api.com/data")
    return resp.json()

# 권장 - 앱 수명주기에 맞춰 하나를 재사용
from contextlib import asynccontextmanager

@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.client = httpx.AsyncClient()
    yield
    await app.state.client.aclose()

app = FastAPI(lifespan=lifespan)
```

`requests` 라이브러리도 마찬가지입니다.
`requests.get()`을 직접 호출하면 매번 새 세션이고, `Session()`을 재사용해야 풀이 살아 있습니다.

이 실수는 **로컬에서는 티가 안 납니다.** 왕복 지연이 1ms도 안 되기 때문입니다.
운영 환경에서 외부 API를 호출할 때 갑자기 느려집니다.

### 함정 2 — CONN_MAX_AGE를 무작정 크게 잡는다

```python
# 흔한 실수 - 크면 좋다고 생각
CONN_MAX_AGE = None      # 무제한 유지
```

worker가 8개면 각자 연결을 붙잡고 놓지 않습니다.
PostgreSQL 기본 `max_connections`가 100인데, worker를 늘리면 금방 넘깁니다.
`FATAL: too many connections` 에러가 납니다.

```python
# 권장 - 유한한 값으로
CONN_MAX_AGE = 60
```

여기서 지난주 내용과 만납니다. **worker 수 × 연결 수 ≤ DB의 max_connections**여야 합니다.
worker를 늘리는 결정이 DB 쪽 한계와 묶여 있다는 뜻입니다.

트래픽이 크면 애플리케이션 대신 PgBouncer 같은 외부 풀러를 두는 게 정석입니다.

### 함정 3 — 타임아웃을 설정하지 않는다

```python
# 흔한 실수 - 상대가 응답하지 않으면 영원히 기다린다
resp = await client.get("https://external-api.com/data")

# 권장 - 단계별로 나눠서 설정
timeout = httpx.Timeout(connect=3.0, read=5.0, write=5.0, pool=1.0)
resp = await client.get("https://external-api.com/data", timeout=timeout)
```

타임아웃이 없으면 외부 API 하나가 멈췄을 때 **내 서버의 worker가 전부 거기 물립니다.**
외부 장애가 내 서비스 전체 장애로 번지는 전형적인 경로입니다.

`connect`와 `read`를 나누는 이유는 원인이 다르기 때문입니다.
connect 타임아웃은 "상대에 못 붙음"(네트워크·방화벽),
read 타임아웃은 "붙었는데 답이 안 옴"(상대가 느림)입니다.

### 함정 4 — TIME_WAIT이 쌓이는 이유를 모른다

```bash
netstat -an | grep TIME_WAIT | wc -l
```

이 숫자가 수만 개라면, 어딘가에서 연결을 계속 새로 맺고 끊고 있다는 뜻입니다.
거의 항상 함정 1이 원인입니다.

커널 파라미터로 억지로 줄이는 방법도 있지만, **먼저 연결을 재사용하도록 코드를 고치는 게 순서**입니다.
증상을 눌러 봤자 원인이 남아 있으면 다른 형태로 다시 나옵니다.

## 트레이드오프

```
연결을 유지하면 (keep-alive)
  얻는 것: handshake·TLS 비용 절약, 지연 감소, TIME_WAIT 감소
  잃는 것: 유휴 연결이 메모리·파일 디스크립터를 계속 점유,
           서버당 동시 연결 수 상한에 더 빨리 도달
  손해인 상황: 클라이언트가 아주 많고 각자 요청은 드문 경우
              (연결 수만 늘고 재사용 이득은 거의 없음)

연결을 매번 끊으면
  얻는 것: 자원을 오래 붙잡지 않음, 연결 상태 관리가 단순
  잃는 것: 요청마다 1.5 RTT 이상 추가, TIME_WAIT 누적
  이득인 상황: 요청 빈도가 극히 낮은 배치성 호출
```

한 가지 관점. **TCP의 신뢰성은 공짜가 아니라 지연으로 지불한 것입니다.**
handshake도, 재전송도, 순서 보장도 전부 시간을 씁니다.

그래서 신뢰성보다 지연이 중요한 영역(실시간 영상, 게임)은 UDP를 씁니다.
HTTP/3가 TCP 대신 UDP 기반 QUIC으로 간 이유도 여기 있습니다.
연결 수립과 TLS 협상을 합쳐서 0~1 RTT로 줄이기 위해서입니다. (3주차 화요일 주제)

## 연결되는 CS 지식

- **OSI/TCP-IP 계층** — 1주차 화요일 내용의 4계층 부분을 확대한 것입니다. 요청 여정의 3단계가 오늘 주제 전체입니다.
- **HTTP/1.1 vs 2 vs 3** — keep-alive를 더 밀고 나간 것이 HTTP/2의 멀티플렉싱이고, TCP 자체를 갈아치운 것이 HTTP/3입니다. (3주차 화요일 주제)
- **프로세스와 스레드, worker 수** — 커넥션 풀 크기는 worker 수와 곱해집니다. 어제 본 튜닝 문제와 직접 묶입니다.
- **소켓과 파일 디스크립터** — 연결 하나가 파일 디스크립터 하나입니다. `Too many open files`의 정체입니다.
- **큐와 버퍼** — 커널의 accept 큐(backlog)가 꽉 차면 연결 요청이 거부됩니다. 목요일 자료구조 주제와 만납니다.

## 다음 행동

```bash
curl -v -o /dev/null -s -w "connect: %{time_connect}s\ntls: %{time_appconnect}s\ntotal: %{time_total}s\n" https://api.example.com/health
```

`time_connect`가 3-way handshake까지, `time_appconnect`가 TLS까지 걸린 시간입니다.
전체 시간 중 인사말이 차지하는 비중을 숫자로 볼 수 있습니다.

같은 명령을 국내 서버와 해외 서버에 각각 실행해 보면
왕복 지연이 커질수록 handshake 비중이 어떻게 불어나는지가 확연히 드러납니다.
