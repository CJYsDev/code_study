## 한 줄 요약

정규화는 **같은 사실을 한 곳에만 저장해서 데이터가 서로 모순되지 않게** 만드는 작업이고,
반정규화는 **조회 속도를 사려고 그 중복 금지를 의도적으로 깨는** 결정입니다.

## 이게 없으면 생기는 문제

### 문제 1 — 같은 사실이 여러 곳에 있으면 반드시 어긋난다

측정 데이터를 이런 테이블 하나에 다 넣었다고 해봅시다.

| id | device_name | device_location | device_owner | value | created_at |
|---|---|---|---|---|---|
| 1 | 온도센서A | 구로공장 1층 | 김철수 | 23.5 | 08-01 |
| 2 | 온도센서A | 구로공장 1층 | 김철수 | 24.1 | 08-01 |
| 3 | 온도센서A | 구로공장 2층 | 김철수 | 23.8 | 08-02 |

3번 행의 위치가 다릅니다. 장비를 옮긴 걸까요, 오타일까요?
**판단할 근거가 없습니다.** 어느 쪽이 진실인지 데이터가 말해주지 않습니다.

여기서 세 가지 이상 현상이 나옵니다.

| 이상 현상 | 상황 |
|---|---|
| 갱신 이상 | 장비 위치가 바뀌면 그 장비의 **모든 행**을 고쳐야 함. 하나라도 놓치면 모순 |
| 삽입 이상 | 아직 측정값이 없는 신규 장비를 등록할 방법이 없음 |
| 삭제 이상 | 마지막 측정 기록을 지우면 **장비 정보까지 같이 사라짐** |

측정 데이터가 1,000만 건이면 장비 이름 하나 바꾸는 데 1,000만 행을 UPDATE해야 합니다.
그 도중에 실패하면 절반만 바뀐 상태로 남습니다. 1주차 수요일에 본 원자성 문제와 만납니다.

### 문제 2 — 반대로, 정규화만 밀어붙이면 조회가 느려진다

정규화를 하면 테이블이 잘게 쪼개집니다. 그럼 화면 하나를 그리는 데 조인이 5~6개 붙습니다.

```sql
SELECT m.value, d.name, l.building, l.floor, o.name, c.company_name
FROM measurement m
JOIN device d   ON m.device_id = d.id
JOIN location l ON d.location_id = l.id
JOIN owner o    ON d.owner_id = o.id
JOIN company c  ON o.company_id = c.id
WHERE m.created_at > '2026-08-01';
```

조인은 공짜가 아닙니다. 데이터가 커질수록 비용이 커지고,
실시간 대시보드처럼 초당 여러 번 호출되는 화면에서는 이게 병목이 됩니다.

**두 문제가 정반대 방향을 가리킵니다.** 그 사이에서 어디에 설 것인지 정하는 게 오늘 주제입니다.

## 비유

**주소록입니다.**

친구 100명의 연락처를 적으면서, 각 친구마다 회사 이름·회사 주소·회사 대표번호를 다 적어뒀습니다.
같은 회사 사람이 10명이면 회사 주소가 10번 적혀 있습니다.

회사가 이사하면 **10군데를 다 고쳐야 합니다.** 하나 빠뜨리면 어느 게 맞는지 모르게 됩니다.

정규화는 "회사 목록"을 따로 만들고, 친구 항목에는 회사 번호만 적는 것입니다.
이사하면 회사 목록 한 줄만 고치면 끝입니다.

대신 친구 연락처를 볼 때마다 **회사 목록을 한 번 더 펼쳐봐야 합니다.** 이게 조인입니다.

반정규화는 여기서 "그래도 회사 이름 정도는 친구 항목에 같이 적어두자"는 결정입니다.
자주 보니까요. 대신 회사 이름이 바뀌면 다시 여러 군데를 고쳐야 한다는 걸 **알고** 받아들이는 겁니다.

단, 이 비유가 놓치는 부분: 주소록은 사람이 눈으로 확인하지만
DB는 잘못된 중복을 아무도 알려주지 않습니다. 조용히 틀린 채로 몇 달이 갑니다.

## 실제로 어떻게 동작하는가

### 정규형

실무에서 필요한 건 사실상 3NF까지입니다.

**1NF — 한 칸에는 값 하나만**

```
잘못됨: sensor_types = "온도,습도,조도"
올바름: 행을 나누거나, 별도 테이블로 분리
```

**2NF — 기본키 일부에만 의존하는 컬럼을 분리**

복합키 `(device_id, created_at)`인 테이블에 `device_name`이 있다면,
이건 `device_id`에만 의존합니다. 분리 대상입니다.

**3NF — 키가 아닌 컬럼에 의존하는 컬럼을 분리**

```
measurement(id, device_id, device_name, device_location)
                            ^^^^^^^^^^^^^^^^^^^^^^^^^^
                            device_id에 딸린 정보 -> device 테이블로
```

한 문장으로 줄이면 이렇습니다.

> **모든 컬럼이 "키에만, 키 전체에, 키 외에는 아무것에도" 의존하게 만든다.**

### 정규화한 모습

```python
# Django
class Location(models.Model):
    building = models.CharField(max_length=100)
    floor = models.IntegerField()

class Device(models.Model):
    name = models.CharField(max_length=100)
    location = models.ForeignKey(Location, on_delete=models.PROTECT)

class Measurement(models.Model):
    device = models.ForeignKey(Device, on_delete=models.CASCADE)
    value = models.FloatField()
    created_at = models.DateTimeField(db_index=True)
```

장비 위치가 바뀌면 `Device` 한 행만 고칩니다. 측정 데이터는 손대지 않습니다.

### 반정규화 — 언제, 어떻게

**전제: 먼저 측정해야 합니다.** 느릴 것 같아서가 아니라, 느린 걸 확인하고 하는 겁니다.

**유형 1 — 컬럼 복사**

```python
class Measurement(models.Model):
    device = models.ForeignKey(Device, on_delete=models.CASCADE)
    device_name = models.CharField(max_length=100)   # 복사본
    value = models.FloatField()
```

조인 없이 장비 이름을 얻습니다. 대신 장비 이름이 바뀌면 동기화해야 합니다.

**유형 2 — 집계 컬럼 (가장 실용적)**

```python
class Device(models.Model):
    name = models.CharField(max_length=100)
    alert_count = models.IntegerField(default=0)     # 미리 세어둔 값
    latest_value = models.FloatField(null=True)      # 최신값 캐시
```

`COUNT(*)`를 매번 하지 않아도 됩니다.
1,000만 건을 세는 것과 컬럼 하나를 읽는 것의 차이입니다.

**유형 3 — 이력성 스냅샷 (이건 반정규화가 아닙니다)**

```python
class Order(models.Model):
    product = models.ForeignKey(Product, on_delete=models.PROTECT)
    product_name = models.CharField(max_length=200)   # 주문 시점의 이름
    price = models.DecimalField(max_digits=10, decimal_places=2)  # 주문 시점의 가격
```

**중요한 구분입니다.**
상품 가격이 나중에 바뀌어도 **과거 주문서의 가격은 그때 값이어야 맞습니다.**
이건 중복이 아니라 **다른 사실**입니다. 시점이 다르니까요.

이런 컬럼은 "동기화해야 할 중복"이 아니라 "보존해야 할 기록"입니다.
반정규화로 착각해서 지우면 안 됩니다.

### 동기화를 어떻게 유지하나

반정규화의 진짜 비용은 저장 공간이 아니라 **동기화 책임**입니다.

```python
# 방법 1 - 시그널 (Django). 편하지만 흐름이 안 보임
from django.db.models.signals import post_save

@receiver(post_save, sender=Alert)
def update_alert_count(sender, instance, created, **kwargs):
    if created:
        Device.objects.filter(id=instance.device_id).update(
            alert_count=F("alert_count") + 1
        )
```

```python
# 방법 2 - 명시적으로 같은 트랜잭션에서 처리. 흐름이 보임
with transaction.atomic():
    Alert.objects.create(device_id=device_id, level="warning")
    Device.objects.filter(id=device_id).update(
        alert_count=F("alert_count") + 1
    )
```

`F()`를 쓰는 이유가 있습니다.

```python
# 흔한 실수 - 읽고 쓰는 사이에 다른 요청이 끼어들면 값이 유실됨
device.alert_count = device.alert_count + 1
device.save()

# 권장 - DB에서 직접 증가시킨다
Device.objects.filter(id=device_id).update(alert_count=F("alert_count") + 1)
```

1주차 수요일에 본 lost update 문제입니다. 정확히 같은 함정이 여기서 재현됩니다.

시그널은 편하지만 **어디서 값이 바뀌는지 코드만 봐서는 모릅니다.**
디버깅이 어려워지므로, 팀 규모가 작을수록 명시적 방법을 권합니다.

## 주니어가 자주 빠지는 함정

### 함정 1 — 측정 없이 반정규화부터 한다

```
"조인이 5개나 되네, 느릴 것 같은데 미리 합쳐두자"
```

조인은 생각보다 안 느립니다. 인덱스가 제대로 걸려 있으면 대부분 문제없습니다.

실제 느린 원인은 보통 다른 데 있습니다.

- 인덱스가 없어서 (2주차 수요일)
- N+1 쿼리 (1주차 목요일)
- 불필요하게 전체 컬럼을 가져와서

**순서는 항상 이렇습니다.**

```
1. EXPLAIN으로 실제 병목 확인
2. 인덱스 추가 / 쿼리 수정 / N+1 제거
3. 그래도 느리면 캐시(Redis)
4. 그래도 안 되면 반정규화
```

반정규화는 **되돌리기 어렵습니다.** 이미 쌓인 데이터를 다 마이그레이션해야 하니까요.
가장 마지막 카드로 남겨둡니다.

### 함정 2 — N+1을 정규화 탓으로 돌린다

```python
# 흔한 실수 - 이걸 보고 "테이블을 합치자"고 결론냄
for m in Measurement.objects.all()[:100]:
    print(m.device.name)          # 100번 추가 쿼리

# 권장 - 조인 한 번으로 끝난다
for m in Measurement.objects.select_related("device")[:100]:
    print(m.device.name)          # 쿼리 1번
```

`select_related`는 조인해서 한 번에 가져옵니다(정방향 FK).
`prefetch_related`는 쿼리를 2번 날려 파이썬에서 합칩니다(역방향, M2M).

이 두 줄로 해결될 문제를 스키마 변경으로 풀려는 게 흔한 과잉 대응입니다.

### 함정 3 — 반정규화 컬럼을 갱신하는 경로가 여러 개다

```python
# 위험 - alert_count를 건드리는 곳이 3군데
def create_alert_api(...):      # 여기서 +1
def bulk_import_alerts(...):    # 여기서도 +1
def admin_delete_alert(...):    # 여기서 -1 하는 걸 깜빡함
```

한 군데라도 빠뜨리면 값이 어긋납니다. 그리고 **아무도 에러를 내지 않습니다.**
몇 달 뒤 "숫자가 안 맞는데요"라는 문의로 알게 됩니다.

대응은 두 가지입니다.

- **갱신 경로를 하나로 모읍니다.** 함수 하나를 만들고 모두 그걸 통하게 합니다.
- **정합성 검증 배치**를 만들어 둡니다. 주기적으로 실제 값과 비교해 어긋나면 알립니다.

```python
# 검증 배치 예시
def verify_alert_counts():
    for device in Device.objects.all():
        actual = Alert.objects.filter(device=device).count()
        if device.alert_count != actual:
            logger.warning("불일치: device=%s 저장값=%s 실제=%s",
                           device.id, device.alert_count, actual)
```

반정규화를 도입할 때 **이 배치까지 같이 만드는 것이 세트**입니다.

### 함정 4 — on_delete를 생각 없이 CASCADE로 둔다

```python
# 위험 - 장비를 지우면 측정 데이터가 전부 사라진다
device = models.ForeignKey(Device, on_delete=models.CASCADE)

# 권장 - 참조 중이면 삭제를 막는다
device = models.ForeignKey(Device, on_delete=models.PROTECT)
```

정규화의 핵심은 참조 무결성인데, `CASCADE`는 그걸 **연쇄 삭제**로 실현합니다.
관리자 화면에서 장비 하나 지웠다가 측정 데이터 수백만 건이 함께 날아가는 사고가 실제로 자주 납니다.

| 옵션 | 동작 | 언제 |
|---|---|---|
| `CASCADE` | 부모 삭제 시 자식도 삭제 | 자식이 부모 없이 의미 없을 때 |
| `PROTECT` | 자식이 있으면 삭제 거부 | 기본으로 삼을 만함 |
| `SET_NULL` | 자식의 FK를 NULL로 | 참조만 끊고 데이터는 남길 때 |

기본을 `PROTECT`로 두고, CASCADE가 정말 맞는 곳만 골라 쓰는 편이 안전합니다.

## 트레이드오프

```
정규화하면
  얻는 것: 데이터 정합성, 갱신이 한 곳에서 끝남, 저장 공간 절약,
           스키마가 의미를 정확히 표현
  잃는 것: 조인 비용, 쿼리가 길어짐, 화면 하나에 여러 테이블이 얽힘
  손해인 상황: 읽기가 압도적으로 많은 분석/집계 시스템,
              실시간 대시보드처럼 응답 시간이 엄격한 경우

반정규화하면
  얻는 것: 조인 제거로 조회 가속, 쿼리 단순화
  잃는 것: 데이터 불일치 위험, 갱신 로직 복잡도, 저장 공간,
           그리고 되돌리기 어려움
  전제 조건: 실제로 측정해서 병목임을 확인했을 것,
            동기화 경로가 하나일 것, 검증 수단이 있을 것
```

세 가지 관점을 덧붙입니다.

**첫째, 이건 "옳고 그름"이 아니라 "무엇을 살 것인가"입니다.**
정규화는 정합성을 사고 속도를 냅니다. 반정규화는 그 반대입니다.
어느 쪽이 정답이 아니라, 이 시스템에서 무엇이 더 비싼지가 답을 정합니다.

**둘째, 시스템 성격에 따라 기본값이 다릅니다.**

| | 기본 방향 |
|---|---|
| OLTP (주문, 예약 등 트랜잭션 처리) | 정규화 |
| OLAP (분석, 리포트, 대시보드) | 반정규화 (스타 스키마 등) |

DICONAI처럼 **센서 데이터 수집(쓰기 많음) + 모니터링 대시보드(읽기 많음)**가 공존하면,
두 성격이 한 시스템에 섞입니다. 이럴 때는 테이블을 나누는 게 정석입니다.
원본은 정규화해서 쌓고, 대시보드용 집계 테이블을 따로 유지하는 식입니다.

**셋째, 반정규화 전에 캐시를 먼저 검토합니다.**
Redis에 집계 결과를 올려두면, 스키마를 안 건드리고 같은 효과를 얻습니다.
캐시는 지우면 그만이라 되돌리기 쉽습니다. 반정규화는 그렇지 않습니다.
"연결고리"를 잡는 관점에서 보면, Redis가 왜 그 자리에 있는지가 여기서 설명됩니다.

## 연결되는 CS 지식

- **인덱스와 B-tree** — 2주차 수요일. 조회를 빠르게 하는 다른 답입니다. 반정규화보다 먼저 시도할 카드입니다.
- **트랜잭션과 ACID** — 1주차 수요일. 반정규화 컬럼 갱신은 원본 변경과 **같은 트랜잭션**에 있어야 합니다. `F()`를 쓰는 이유도 lost update 방지입니다.
- **시간복잡도** — 1주차 목요일. 조인은 데이터 크기에 따라 비용이 늘고, 미리 계산해둔 컬럼은 O(1)입니다. 시간-공간 맞바꿈의 또 다른 사례입니다.
- **캐시와 Redis** — 반정규화와 같은 목적, 다른 층위의 해법입니다. 되돌리기 쉬운 쪽을 먼저 씁니다.
- **CQRS** — 읽기 모델과 쓰기 모델을 아예 분리하는 설계. 오늘의 갈등을 구조로 푼 답입니다.

## 다음 행동

```sql
-- 지금 느린 쿼리에 조인이 정말 병목인지 확인
EXPLAIN ANALYZE
SELECT m.value, d.name
FROM measurement m
JOIN device d ON m.device_id = d.id
WHERE m.created_at > '2026-08-01';
```

실행 계획에서 `Hash Join`이나 `Nested Loop`가 차지하는 시간을 봅니다.
전체 시간의 대부분이 **조인이 아니라 스캔**에 쓰이고 있다면,
답은 반정규화가 아니라 인덱스입니다.

이 확인이 3주차 금요일 통합 과제와 그대로 이어집니다.
