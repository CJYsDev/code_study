# 배열과 연결리스트 — 무엇을 맞바꾼 자료구조인가

1일 1CS / 2주차 목요일 / 자료구조·알고리즘
티어: C (7섹션 전부)

---

## 한 줄 요약

배열은 **메모리에 붙어 있어서** 아무 데나 바로 접근할 수 있는 대신 중간을 건드리기 어렵고,
연결리스트는 **흩어져 있어서** 중간을 고치기 쉬운 대신 순서대로만 갈 수 있습니다.

---

## 이게 없으면 생기는 문제

### 문제 1 — 왜 `pop(0)`이 느린지 설명할 수 없다

1주차 목요일에 이런 함정을 봤습니다.

```python
queue.pop(0)      # O(n)
queue.pop()       # O(1)
```

같은 리스트, 같은 메서드인데 앞을 빼면 느리고 뒤를 빼면 빠릅니다.
"그렇게 외워라"로 끝내면 다음에 비슷한 상황에서 또 틀립니다.

오늘 내용을 알면 **왜 그런지가 한 문장으로 나옵니다.**
그리고 `insert(0, x)`도, 문자열 이어붙이기도, 리스트 중간 삭제도 전부 같은 이유라는 게 보입니다.

### 문제 2 — 자료구조를 고르는 기준이 없다

"리스트 쓸까 딕셔너리 쓸까 deque 쓸까"를 감으로 정하게 됩니다.

기준은 사실 단순합니다.

> 이 데이터를 **어떻게 접근**하고 **어디를 자주 고치는가**

이 질문에 답하려면 각 자료구조가 메모리에 어떻게 놓여 있는지를 알아야 합니다.
오늘 배우는 두 가지가 거의 모든 자료구조의 **바닥**입니다.
스택, 큐, 해시테이블, 트리가 전부 이 둘 중 하나 위에 얹혀 있습니다.

---

## 비유

**배열은 극장 좌석이고, 연결리스트는 보물찾기입니다.**

극장에서 15번 좌석을 찾는 데는 계산 한 번이면 됩니다.
1번 좌석 위치를 알고 좌석 폭을 알면 15번이 어디인지 바로 나옵니다.
대신 5번 자리에 사람을 한 명 끼워 넣으려면 **6번부터 끝까지 전부 한 칸씩 이동**해야 합니다.

보물찾기는 첫 번째 쪽지를 열어야 두 번째 위치를 알 수 있습니다.
15번째 쪽지를 보려면 14장을 순서대로 열어야 합니다.
대신 중간에 쪽지 하나를 끼워 넣는 건 쉽습니다.
**앞 쪽지가 가리키는 곳만 새 쪽지로 바꾸면** 됩니다. 나머지는 그대로 둡니다.

단, 이 비유가 놓치는 부분: 극장 좌석은 흩어져 있으나 붙어 있으나 찾는 수고가 비슷하지만,
실제 메모리에서는 **붙어 있는 쪽이 압도적으로 빠릅니다.** CPU 캐시 때문입니다.
아래에서 이어집니다.

---

## 실제로 어떻게 동작하는가

### 메모리에 놓인 모양

```
배열 — 연속된 공간
주소:  1000  1008  1016  1024  1032
값:   [ 10 ][ 20 ][ 30 ][ 40 ][ 50 ]

3번째 원소 위치 = 시작주소 + (2 × 크기) = 1000 + 16 = 1016
계산 한 번. O(1)
```

```
연결리스트 — 흩어진 공간
[ 10 | 주소2400 ] --> [ 20 | 주소1700 ] --> [ 30 | null ]
  주소 1000              주소 2400            주소 1700

3번째 원소를 보려면 1번 -> 2번 -> 3번 순서로 따라가야 함. O(n)
```

배열이 인덱스 접근을 `O(1)`로 하는 건 **주소를 계산할 수 있기 때문**입니다.
연결리스트는 각 노드가 다음 주소를 들고 있을 뿐이라 계산이 불가능합니다.

### 연산별 비교

| 연산 | 배열 | 연결리스트 |
|---|---|---|
| i번째 접근 | O(1) | O(n) |
| 맨 뒤 추가 | O(1) (평균) | O(1) |
| 맨 앞 추가/삭제 | O(n) | O(1) |
| 중간 삽입/삭제 | O(n) | O(1) — 단, 위치를 이미 알고 있을 때 |
| 값으로 검색 | O(n) | O(n) |
| 추가 메모리 | 없음 | 노드마다 포인터 |

중간 삽입에 붙은 단서가 중요합니다.
연결리스트의 중간 삽입이 `O(1)`인 건 **그 위치를 이미 잡고 있을 때**입니다.
위치를 찾는 것부터 하면 `O(n)`이라 결국 배열과 다를 게 없습니다.

### 배열의 크기가 늘어나는 방식

Python의 `list`는 배열인데, 크기가 고정이 아닙니다. 어떻게 하는 걸까요.

```
꽉 차면 -> 더 큰 공간을 새로 할당 -> 기존 값 전부 복사 -> 옛 공간 반납
```

복사가 일어나는 순간은 `O(n)`입니다.
그런데 매번 일어나는 게 아니라 **용량을 넉넉히(보통 1.5~2배) 잡아두기 때문에**
`append`를 n번 했을 때 전체 비용을 n으로 나누면 `O(1)`이 됩니다.

이걸 **분할상환(amortized) O(1)**이라고 합니다.
"가끔 비싸지만 평균적으로 싸다"는 뜻입니다.

### 캐시 지역성 — 표에 안 나오는 진짜 차이

여기가 실무에서 제일 중요한데 Big-O 표에는 안 나옵니다.

CPU는 메모리에서 값 하나를 읽을 때 **그 주변까지 통째로 캐시에 담아옵니다.**
(캐시 라인, 보통 64바이트)

배열은 값들이 붙어 있으므로, 하나를 읽으면 **다음 몇 개가 이미 캐시에 와 있습니다.**
연결리스트는 흩어져 있어서 매번 메모리를 새로 찾아가야 합니다.

```
같은 O(n) 순회인데도
배열       : 캐시 적중률 높음 -> 빠름
연결리스트 : 매번 캐시 미스   -> 실측으로 수 배에서 수십 배 느림
```

2주차 월요일에 컨텍스트 스위칭의 진짜 비용이 캐시 무효화였던 것과 같은 이야기입니다.
**메모리 접근 패턴이 복잡도만큼 중요합니다.**

그래서 현대 하드웨어에서는 "중간 삽입이 많으니 연결리스트"라는 판단이
자주 틀립니다. 배열을 쓰고 통째로 다시 만드는 게 더 빠른 경우가 흔합니다.

### Python에서는 무엇이 무엇인가

| 타입 | 실제 구조 | 특징 |
|---|---|---|
| `list` | 동적 배열 | 인덱스 O(1), 앞쪽 조작 O(n) |
| `collections.deque` | 이중 연결 리스트 (블록 단위) | 양쪽 끝 O(1), 인덱스 접근 O(n) |
| `str`, `tuple` | 불변 배열 | 수정 불가 |

Python에는 순수 연결리스트 자료형이 없습니다.
`deque`가 가장 가깝지만, 성능을 위해 여러 원소를 한 블록에 담는 하이브리드 구조입니다.

## 주니어가 자주 빠지는 함정

### 함정 1 — 큐를 리스트로 만든다

```python
# 흔한 실수 - pop(0)이 매번 전체를 앞으로 당긴다
queue = []
queue.append(task)
task = queue.pop(0)        # O(n)

# 권장 - deque는 양쪽 끝이 O(1)
from collections import deque

queue = deque()
queue.append(task)
task = queue.popleft()     # O(1)
```

이제 이유를 말할 수 있습니다.
리스트는 연속된 메모리라, 0번을 빼면 **나머지 전부를 한 칸씩 앞으로 이동**시켜야
"i번째 = 시작주소 + i × 크기" 공식이 계속 성립하기 때문입니다.

### 함정 2 — 리스트 중간을 순회하면서 삭제한다

```python
# 흔한 실수 - 삭제할 때마다 뒤가 당겨져서 원소를 건너뛴다
for item in items:
    if item.is_expired:
        items.remove(item)      # 순회 중 리스트가 변형됨

# 권장 - 새 리스트를 만든다
items = [item for item in items if not item.is_expired]
```

`remove`는 두 번 `O(n)`입니다. 찾는 데 한 번, 뒤를 당기는 데 한 번.
게다가 순회 중에 인덱스가 밀려서 **일부 원소를 건너뜁니다.** 조용히 잘못된 결과가 나옵니다.

리스트 컴프리헨션은 전체를 한 번만 훑어서 `O(n)`이고, 버그도 없습니다.

### 함정 3 — 문자열을 루프에서 이어붙인다

```python
# 흔한 실수 - 문자열은 불변이라 매번 새로 만들어 전체를 복사한다
result = ""
for row in rows:
    result += f"{row.id},{row.value}\n"      # 전체 O(n²)

# 권장 - 조각을 모았다가 한 번에 합친다
parts = [f"{row.id},{row.value}\n" for row in rows]
result = "".join(parts)                      # O(n)
```

문자열은 배열이고 **불변**입니다.
`+=` 할 때마다 새 배열을 할당하고 기존 내용을 전부 복사합니다.

로그 100줄에서는 아무도 눈치채지 못하고, CSV 10만 줄에서 터집니다.
1주차 목요일에 본 "로컬에서는 절대 안 터진다"의 또 다른 사례입니다.

### 함정 4 — QuerySet을 리스트처럼 반복해서 쓴다

```python
# 흔한 실수 - QuerySet은 배열이 아니라 게으른 쿼리 객체다
devices = Device.objects.filter(is_active=True)

count = len(devices)              # 전체를 메모리에 올림
for d in devices:                 # 캐시되어 있으면 재사용, 아니면 또 조회
    ...
if devices:                       # 상황에 따라 또 평가
    ...

# 권장 - 필요한 형태로 한 번만 확정한다
count = Device.objects.filter(is_active=True).count()     # DB에서 세기

devices = list(Device.objects.filter(is_active=True))     # 명시적으로 한 번 로드
for d in devices:
    ...
```

`len()`은 전체를 파이썬 객체로 만들어 메모리에 올리고, `.count()`는 DB에서 숫자만 받아옵니다.
데이터가 많을수록 차이가 큽니다.

"내가 지금 다루는 게 진짜 배열인가, 아니면 배열처럼 보이는 다른 것인가"를
구분하는 습관이 필요합니다.

## 트레이드오프

```
배열을 쓰면
  얻는 것: O(1) 인덱스 접근, 캐시 지역성으로 실제 순회가 매우 빠름,
           추가 메모리 없음
  잃는 것: 앞/중간 삽입·삭제가 O(n), 크기 확장 시 전체 복사 발생
  손해인 상황: 앞쪽 조작이 빈번한 큐, 원소가 매우 크고 이동 비용이 큰 경우

연결리스트를 쓰면
  얻는 것: 위치를 알고 있다면 삽입·삭제가 O(1), 크기 확장에 복사 없음
  잃는 것: 인덱스 접근 O(n), 노드마다 포인터 메모리 추가,
           캐시 미스로 실측 성능이 나쁨
  손해인 상황: 인덱스 접근이나 순회가 잦은 경우 (대부분의 실무 상황)
```

솔직하게 정리하면 이렇습니다.

**실무에서 연결리스트를 직접 구현해 쓸 일은 거의 없습니다.**
Python에서는 `list`와 `deque`로 대부분 해결되고, 캐시 지역성 때문에
이론상 유리해 보이는 상황에서도 배열이 이기는 경우가 많습니다.

그럼에도 배우는 이유는 두 가지입니다.

- **다른 자료구조의 부품**입니다. 해시테이블의 충돌 처리, 트리, 그래프 인접 리스트가 전부 이 구조 위에 있습니다.
- **"메모리에 어떻게 놓여 있는가"가 성능을 좌우한다**는 감각을 여기서 처음 잡습니다. 이 감각이 인덱스, 캐시, DB 블록 설계로 계속 이어집니다.

## 연결되는 CS 지식

- **시간복잡도와 Big-O** — 1주차 목요일 함정 2(`pop(0)`)의 근본 원인이 오늘 내용입니다.
- **컨텍스트 스위칭과 캐시** — 이번 주 월요일에 본 캐시 무효화 비용이, 여기서는 캐시 지역성으로 나타납니다. 같은 하드웨어 특성의 다른 얼굴입니다.
- **B-tree와 인덱스** — 어제 본 "노드 하나를 뚱뚱하게"가 정확히 캐시/블록 지역성을 노린 설계입니다. 배열의 장점을 트리에 끌어온 것입니다.
- **해시테이블** — 배열 위에 얹혀 있고, 충돌 처리에 연결리스트를 씁니다. 두 구조가 함께 쓰이는 대표 사례입니다. (3주차 목요일 주제)
- **스택과 큐** — 둘 다 배열로도 연결리스트로도 만들 수 있습니다. 어느 쪽을 고를지가 오늘 배운 트레이드오프입니다. (4주차 목요일 주제)

## 다음 행동

```python
import timeit

setup = "from collections import deque; n = 100000"

print(timeit.timeit("l = list(range(n));  [l.pop(0) for _ in range(n)]",
                    setup=setup, number=1))
print(timeit.timeit("d = deque(range(n)); [d.popleft() for _ in range(n)]",
                    setup=setup, number=1))
```

n을 10,000 / 50,000 / 100,000으로 바꿔가며 돌려보면
리스트 쪽은 시간이 **제곱으로** 늘고 deque는 선형으로 늘어납니다.
`O(n²)`와 `O(n)`의 차이를 눈으로 보는 가장 짧은 실험입니다.
