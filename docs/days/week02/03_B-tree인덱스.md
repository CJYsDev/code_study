# B-tree 인덱스 — 왜 B-tree를 쓰는가

1일 1CS / 2주차 수요일 / 데이터베이스

## 한 줄 요약

인덱스는 조회를 `O(n)`에서 `O(log n)`으로 바꾸는 **정렬된 지름길**이고,
그 자료구조로 B-tree를 쓰는 이유는 **디스크를 읽는 횟수를 최소화**하기 위해서입니다.

---

## 이게 없으면 생기는 문제

### 문제 1 — 한 건을 찾으려고 전부 읽는다

측정 데이터가 1,000만 건 쌓인 테이블에서 장비 하나의 데이터를 찾습니다.

```sql
SELECT * FROM measurement WHERE device_id = 42;
```

인덱스가 없으면 DB는 **1번 행부터 1,000만 번 행까지 전부 읽어서** `device_id`를 확인합니다.
이걸 Full Scan(PostgreSQL에서는 Seq Scan)이라고 합니다.

결과가 10건뿐이어도 1,000만 건을 읽습니다. 목요일에 본 `O(n)`입니다.
데이터가 2배 쌓이면 조회 시간도 2배가 됩니다.

**여기서 진짜 문제는 "느리다"가 아니라 "점점 느려진다"입니다.**
서비스 초기에 200ms였던 API가 1년 뒤 8초가 됩니다.
코드는 한 줄도 안 바뀌었는데 말입니다.

### 문제 2 — 디스크 읽기는 메모리 읽기와 비용 단위가 다르다

지난주에 Big-O를 배울 때 연산 횟수를 셌습니다. 그런데 DB에서는 단위가 다릅니다.

| 접근 대상 | 대략적인 지연 |
|---|---|
| CPU 캐시 | 1ns 이하 |
| 메모리 | 100ns |
| SSD | 100,000ns (0.1ms) |
| HDD | 10,000,000ns (10ms) |

메모리와 SSD가 **1,000배** 차이납니다.
그래서 DB 자료구조를 설계할 때 최적화 대상은 "연산 횟수"가 아니라 **"디스크를 몇 번 읽는가"**입니다.

이 한 줄이 왜 이진 탐색 트리가 아니라 B-tree인지를 전부 설명합니다.

---

## 비유

**책 뒤의 색인입니다.** (1주차 목요일에 나왔던 그 비유입니다)

책 전체를 뒤지지 않고 색인에서 단어를 찾으면 페이지 번호가 나옵니다.
색인은 **가나다순으로 정렬되어 있어서** 원하는 항목까지 몇 번 만에 도달합니다.

여기서 두 가지가 더 보입니다.

- **색인은 공간을 차지합니다.** 책이 두꺼워집니다.
- **책 내용이 바뀌면 색인도 고쳐야 합니다.** 그냥 두면 잘못된 페이지를 가리킵니다.

인덱스도 똑같습니다. 저장 공간을 더 쓰고, INSERT/UPDATE 때마다 같이 갱신해야 합니다.

단, 이 비유가 놓치는 부분: 책 색인은 한 페이지에 여러 항목이 있고
우리는 그 페이지를 통째로 봅니다. B-tree가 정확히 이 방식으로 동작하는데,
왜 그렇게 하는지가 아래에서 핵심입니다.

---

## 실제로 어떻게 동작하는가

### 왜 이진 탐색 트리가 아닌가

이진 탐색 트리도 `O(log n)`입니다. 그런데 DB는 안 씁니다.

```
이진 트리: 노드 하나에 값 1개, 자식 2개
  1,000만 건 -> 높이 약 23  -> 디스크 읽기 23번

B-tree:   노드 하나에 값 수백 개, 자식 수백 개
  1,000만 건 -> 높이 약 3~4 -> 디스크 읽기 3~4번
```

둘 다 `O(log n)`인데 **밑(base)이 다릅니다.**
이진 트리는 log₂, B-tree는 log₂₅₆ 같은 식입니다.

디스크는 바이트 단위가 아니라 **블록 단위(보통 8KB)로 읽습니다.**
1바이트를 읽으나 8KB를 읽으나 비용이 거의 같습니다.
그렇다면 한 번 읽을 때 최대한 많이 담는 게 이득입니다.

B-tree의 노드 하나 = 디스크 블록 하나입니다.
8KB에 키를 수백 개 욱여넣어서, 한 번 읽을 때마다 후보를 수백 분의 1로 줄입니다.

**이게 B-tree의 전부입니다.** "디스크 읽기 횟수를 줄이려고 노드를 뚱뚱하게 만든 트리".

### 구조

```
                    [ 50 | 100 ]                     <- 루트 (항상 메모리에 있음)
                   /      |      \
        [10|20|30]   [60|70|80]   [110|120]          <- 중간 노드
         /  |  \       /  |  \      /   \
      [리프][리프][리프] ...                          <- 리프: 실제 데이터 위치
       <-> <-> <->                                   <- 리프끼리 연결됨
```

세 가지 성질이 중요합니다.

**1. 모든 리프의 깊이가 같습니다.**
어떤 값을 찾든 읽는 횟수가 동일합니다. 성능이 예측 가능합니다.

**2. 리프끼리 양방향으로 연결되어 있습니다.** (B+tree)
그래서 범위 조회가 빠릅니다. 시작점만 찾으면 옆으로 쭉 훑으면 됩니다.

```sql
-- 시작점을 O(log n)으로 찾고, 그 뒤는 리프를 순차적으로 따라간다
SELECT * FROM measurement WHERE created_at BETWEEN '2026-08-01' AND '2026-08-07';
```

**3. 정렬되어 있습니다.**
`ORDER BY`가 인덱스 순서와 같으면 정렬 작업 자체가 사라집니다.

### 인덱스를 만드는 법

```python
# Django
class Measurement(models.Model):
    device = models.ForeignKey(Device, on_delete=models.CASCADE)   # FK는 자동 생성
    created_at = models.DateTimeField(db_index=True)               # 단일 컬럼
    value = models.FloatField()

    class Meta:
        indexes = [
            models.Index(fields=["device", "-created_at"]),        # 복합 인덱스
        ]
```

```sql
-- SQL로는
CREATE INDEX idx_measurement_device_created ON measurement (device_id, created_at DESC);
```

### 복합 인덱스의 순서 규칙

복합 인덱스에서 **컬럼 순서가 전부**입니다.

`(device_id, created_at)` 인덱스가 있을 때:

| 쿼리 조건 | 인덱스 사용 | 이유 |
|---|---|---|
| `device_id = 42` | 사용함 | 첫 번째 컬럼부터 시작 |
| `device_id = 42 AND created_at > ...` | 사용함 | 순서대로 |
| `created_at > ...` | 못 씀 | 첫 컬럼을 건너뜀 |

전화번호부가 (성, 이름) 순으로 정렬되어 있으면 "김"으로 시작하는 사람은 쉽게 찾지만,
이름이 "철수"인 사람은 전부 뒤져야 하는 것과 같습니다.

이걸 **왼쪽 접두사 규칙(leftmost prefix)**이라고 합니다.

## 주니어가 자주 빠지는 함정

### 함정 1 — 컬럼에 함수를 씌운다

```sql
-- 흔한 실수 - created_at에 인덱스가 있어도 못 쓴다
SELECT * FROM measurement WHERE DATE(created_at) = '2026-08-14';

-- 권장 - 컬럼을 그대로 두고 범위로 바꾼다
SELECT * FROM measurement
WHERE created_at >= '2026-08-14' AND created_at < '2026-08-15';
```

인덱스는 **`created_at`의 값**으로 정렬되어 있지, `DATE(created_at)`의 값으로 정렬된 게 아닙니다.
컬럼을 가공하는 순간 정렬 순서가 깨져서 인덱스를 탈 수 없습니다.

Django ORM에서도 같은 일이 일어납니다.

```python
# 흔한 실수 - __date 룩업이 함수로 변환된다
Measurement.objects.filter(created_at__date=target_date)

# 권장 - 범위 조건으로
Measurement.objects.filter(
    created_at__gte=start,
    created_at__lt=end,
)
```

원칙 하나로 기억하면 됩니다. **왼쪽(컬럼)은 건드리지 말고 오른쪽(값)을 바꿔라.**

### 함정 2 — 컬럼마다 인덱스를 다 건다

```python
# 흔한 실수 - 일단 다 걸어두면 빠르겠지
class Measurement(models.Model):
    device = models.ForeignKey(Device, db_index=True)
    created_at = models.DateTimeField(db_index=True)
    value = models.FloatField(db_index=True)
    status = models.CharField(max_length=20, db_index=True)
    sensor_type = models.CharField(max_length=20, db_index=True)
```

인덱스는 **읽기를 빠르게 하고 쓰기를 느리게 합니다.**
INSERT 한 번에 인덱스 5개를 전부 갱신해야 합니다.
센서 데이터처럼 쓰기가 많은 테이블에서는 이게 치명적입니다.

저장 공간도 늘어납니다. 인덱스가 테이블 본체보다 커지는 경우도 흔합니다.

**실제로 조회 조건에 쓰이는 컬럼에만** 겁니다.
쓰이지 않는 인덱스는 비용만 내고 아무것도 돌려주지 않습니다.

### 함정 3 — 카디널리티가 낮은 컬럼에 인덱스를 건다

```python
# 효과 거의 없음 - status 값이 'normal'/'warning' 두 개뿐이라면
status = models.CharField(max_length=20, db_index=True)
```

전체의 90%가 `normal`이라면, 인덱스를 타고 가도 90%를 읽어야 합니다.
그럴 바에는 그냥 전체 스캔이 낫습니다.

옵티마이저도 이걸 알아서 **인덱스를 만들어놔도 무시합니다.**
"인덱스를 걸었는데 왜 안 타지?"의 흔한 원인 중 하나입니다.

값의 종류가 많을수록(카디널리티가 높을수록) 인덱스 효과가 큽니다.
`device_id`, `email`, `created_at` 같은 것이 좋은 후보입니다.

### 함정 4 — 인덱스만 걸고 확인하지 않는다

```sql
EXPLAIN ANALYZE
SELECT * FROM measurement WHERE device_id = 42;
```

읽을 때 볼 것은 딱 두 가지입니다.

| 나오는 것 | 의미 |
|---|---|
| `Seq Scan` | 전체 스캔. 인덱스를 안 탔다 |
| `Index Scan` / `Bitmap Index Scan` | 인덱스를 탔다 |

그리고 `rows` 추정치와 `actual rows`가 크게 다르면
통계가 오래된 것이므로 `ANALYZE`를 실행해줘야 합니다.

Django에서 실제 나가는 SQL 확인:

```python
print(Measurement.objects.filter(device_id=42).query)
```

3주차 금요일 통합 과제가 정확히 이 작업입니다.

## 트레이드오프

```
인덱스를 만들면
  얻는 것: 조회 O(n) -> O(log n), 정렬 비용 제거, 범위 조회 가속
  잃는 것: 저장 공간 추가, INSERT/UPDATE/DELETE 비용 증가,
           옵티마이저가 판단할 후보가 늘어남
  손해인 상황: 쓰기가 압도적으로 많은 테이블 (로그, 시계열 원본 데이터),
              카디널리티가 낮은 컬럼, 테이블 자체가 작은 경우
```

이 거래의 본질은 **시간과 공간의 맞바꿈**입니다.
1주차 목요일에 리스트를 set으로 바꾼 것과 같은 형태입니다.
미리 정리해두는 비용을 내고, 찾는 비용을 줄입니다.

하나 더. **"인덱스를 걸었는데 안 빨라졌다"는 대부분 인덱스 문제가 아닙니다.**
쿼리가 인덱스를 못 타게 쓰였거나(함정 1), 애초에 조회할 행이 많거나,
혹은 병목이 DB가 아니라 다른 곳(N+1, 네트워크, 직렬화)에 있습니다.
그래서 인덱스를 걸기 전에 `EXPLAIN`으로 **지금 무엇이 느린지 먼저 확인**하는 게 순서입니다.

## 연결되는 CS 지식

- **시간복잡도와 Big-O** — 1주차 목요일의 색인 비유가 여기서 실제 구현으로 나타납니다. `O(n)` → `O(log n)`이 인덱스 전부입니다.
- **해시테이블** — Hash 인덱스는 `O(1)`이지만 범위 조회와 정렬이 안 됩니다. 그래서 DB 기본은 B-tree입니다. (3주차 목요일 주제)
- **트랜잭션과 ACID** — 인덱스도 트랜잭션 대상입니다. INSERT가 느려지는 이유 중 하나가 인덱스 갱신까지 원자적으로 처리하기 때문입니다.
- **디스크 I/O와 블록** — B-tree 설계의 전제입니다. 순차 읽기와 랜덤 읽기의 비용 차이가 WAL 설계와도 같은 뿌리입니다.
- **정규화와 반정규화** — 조인을 줄여 조회를 빠르게 하는 또 다른 방법입니다. 인덱스와 같은 문제의 다른 답입니다. (3주차 수요일 주제)

## 다음 행동

지금 운영 중인 테이블 하나를 골라 이 쿼리를 실행해 보면
어떤 인덱스가 실제로 쓰이고 있는지, 만들어만 놓고 안 쓰는 게 있는지 바로 보입니다.

```sql
SELECT relname, indexrelname, idx_scan
FROM pg_stat_user_indexes
ORDER BY idx_scan ASC;
```

`idx_scan`이 0인 인덱스는 **한 번도 안 쓰인 인덱스**입니다.
쓰기 비용만 내고 있다는 뜻입니다.
