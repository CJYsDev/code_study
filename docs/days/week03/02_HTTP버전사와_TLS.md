# HTTP 버전사와 TLS — 왜 세 번 갈아엎었고 무엇을 협상하는가

1일 1CS / 3주차 화요일 / 네트워크
티어: C (7섹션 전부)

---

## 한 줄 요약

HTTP 1.1 → 2 → 3의 역사는 **"한 번에 하나씩만 처리된다"는 병목을 계층을 하나씩 내려가며 걷어낸 과정**이고,
TLS는 그 위에 **암호화 비용을 최소 왕복으로 얹는 협상 절차**입니다.

---

## 이게 없으면 생기는 문제

### 문제 1 — 연결을 재사용해도 여전히 줄을 선다

2주차 화요일에 keep-alive로 handshake 비용을 없앴습니다. 그런데 문제가 하나 남습니다.

HTTP/1.1은 **한 연결에서 요청 하나가 끝나야 다음 요청을 보낼 수 있습니다.**

```
연결 1: [요청 A ....응답 A] [요청 B ....응답 B] [요청 C ....응답 C]
                ^ A가 3초 걸리면 B와 C는 3초를 그냥 기다린다
```

이걸 **Head-of-Line Blocking**(줄 맨 앞이 막으면 전부 막힘)이라고 합니다.

브라우저는 이걸 우회하려고 **연결을 6~8개씩 엽니다.**
근본 해결이 아니라 줄을 여러 개 만든 것뿐입니다.
서버 입장에서는 연결 수가 6~8배가 되고, 각 연결마다 handshake·TLS 비용을 따로 냅니다.

### 문제 2 — 헤더가 매번 통째로 반복된다

```http
GET /api/sensors/1 HTTP/1.1
Host: api.example.com
User-Agent: Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7) ...
Accept: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Cookie: session=abc123; theme=dark; lang=ko
```

이 헤더가 **요청마다 똑같이** 실려 갑니다. 본문이 200바이트인데 헤더가 800바이트인 상황이 흔합니다.
API를 50번 호출하면 같은 문자열을 50번 보냅니다.

### 문제 3 — 암호화가 없으면 전부 읽힌다

평문 HTTP는 중간에서 누구나 읽고 고칠 수 있습니다.
로그인 토큰, 세션 쿠키, 개인정보가 그대로 노출됩니다.
공용 WiFi에서 특히 위험합니다.

그런데 암호화를 붙이면 **왕복이 더 늘어납니다.** 이 비용을 어떻게 줄이느냐가 TLS 발전사입니다.

## 비유

**창구가 하나인 은행에서 창구를 늘려온 역사입니다.**

- **HTTP/1.0** — 손님 한 명 볼 때마다 은행 문을 닫았다 다시 엽니다. (연결을 매번 새로)
- **HTTP/1.1** — 문은 열어두지만 창구가 하나입니다. 앞사람이 오래 걸리면 뒤가 다 막힙니다.
- **HTTP/2** — 창구 하나에서 여러 손님 업무를 **번갈아 조금씩** 처리합니다. 서류를 잘게 쪼개서 섞어 보냅니다.
- **HTTP/3** — 은행 건물 자체를 바꿉니다. 앞의 개선은 건물 구조(TCP) 때문에 한계가 있었습니다.

TLS는 **업무 전에 하는 신원 확인과 암호 정하기**입니다.
"당신이 진짜 그 은행 맞나요"(인증서 검증), "우리 어떤 방식으로 비밀 얘기할까요"(암호 스위트 협상).
이 절차를 몇 마디에 끝내느냐가 TLS 1.2와 1.3의 차이입니다.

단, 이 비유가 놓치는 부분: HTTP/2의 "번갈아 처리"는 사람이 아니라 **패킷 단위**라
실제로는 거의 동시처럼 느껴집니다. 그리고 은행과 달리 손님 쪽에서도
"이건 먼저 처리해줘"라고 우선순위를 지정할 수 있습니다.

## 실제로 어떻게 동작하는가

### 버전별 비교

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 등장 | 1997 | 2015 | 2022 |
| 전송 계층 | TCP | TCP | QUIC (UDP 기반) |
| 형식 | 텍스트 | 바이너리 프레임 | 바이너리 프레임 |
| 동시 요청 | 연결당 1개 | 멀티플렉싱 | 멀티플렉싱 |
| 헤더 압축 | 없음 | HPACK | QPACK |
| HOL 블로킹 | 응용 계층에서 발생 | TCP 계층에 남아 있음 | 해결됨 |
| 연결 수립 | TCP 3-way + TLS | TCP 3-way + TLS | 1 RTT 또는 0 RTT |

### HTTP/2 — 멀티플렉싱

요청과 응답을 **프레임**이라는 작은 조각으로 쪼개고, 각 조각에 스트림 ID를 붙입니다.

```
연결 하나 위에서
  [스트림1 조각][스트림3 조각][스트림1 조각][스트림2 조각][스트림3 조각]...
  -> 받는 쪽이 ID로 다시 조립
```

요청 A가 느려도 B와 C의 조각은 계속 흘러갑니다. 응용 계층의 HOL 블로킹이 사라집니다.

여기에 **HPACK**으로 헤더를 압축합니다.
양쪽이 이미 주고받은 헤더를 테이블에 저장해두고, 두 번째부터는 **번호만** 보냅니다.
`User-Agent: Mozilla/5.0 ...` 800바이트가 `62` 한 바이트가 됩니다.

### HTTP/2에 남은 문제

멀티플렉싱을 했는데도 병목이 남습니다. **TCP 때문**입니다.

TCP는 "순서대로 빠짐없이 전달"을 보장합니다.
그래서 패킷 하나가 유실되면, **그 뒤에 도착한 패킷을 전부 붙잡아둡니다.**
재전송이 도착할 때까지 애플리케이션에 올려주지 않습니다.

```
스트림 1의 패킷이 유실됨
-> TCP는 스트림 2, 3의 패킷도 붙잡아둠 (순서 보장 때문에)
-> 응용 계층에서는 멀티플렉싱했는데 전송 계층에서 다시 막힘
```

HOL 블로킹이 7계층에서 4계층으로 **내려갔을 뿐**입니다.

### HTTP/3 — TCP를 버린다

TCP 안에서는 해결이 안 되니, UDP 위에 새 프로토콜을 만들었습니다. **QUIC**입니다.

UDP는 순서 보장도 재전송도 없는 대신 **간섭하지 않습니다.**
QUIC이 그 위에서 스트림별로 따로 순서와 재전송을 관리합니다.

```
스트림 1의 패킷 유실 -> 스트림 1만 기다림. 2, 3은 그대로 진행
```

여기에 더해 **연결 수립과 TLS 협상을 하나로 합쳤습니다.**

```
TCP + TLS 1.3 : 3-way(1.5 RTT) + TLS(1 RTT)  = 약 2.5 RTT
QUIC          : 1 RTT (재접속 시 0 RTT도 가능)
```

2주차 화요일에 본 "인사말이 실제 데이터보다 오래 걸린다"는 문제를 근본에서 줄인 것입니다.

또 하나, **연결 마이그레이션**이 됩니다.
TCP 연결은 (출발지 IP, 포트, 목적지 IP, 포트) 네 개로 식별되어서,
WiFi에서 LTE로 바꾸면 IP가 바뀌어 연결이 끊깁니다.
QUIC은 연결 ID로 식별해서 IP가 바뀌어도 이어집니다. 모바일에서 체감 차이가 큽니다.

### TLS 핸드셰이크

```
TLS 1.2 (2 RTT)
  클라이언트 --- ClientHello (지원 암호 목록) ------> 서버
  클라이언트 <-- ServerHello + 인증서 -------------- 서버
  클라이언트 --- 키 교환 + Finished ---------------> 서버
  클라이언트 <-- Finished -------------------------- 서버

TLS 1.3 (1 RTT)
  클라이언트 --- ClientHello + 키 공유 시도 -------> 서버
  클라이언트 <-- ServerHello + 인증서 + Finished --- 서버
  클라이언트 --- Finished -------------------------> 서버
```

TLS 1.3은 **클라이언트가 미리 키 재료를 같이 보냅니다.**
서버가 그중 하나를 고르면 되니 왕복이 하나 줄어듭니다.
동시에 취약한 옛 암호 알고리즘들을 목록에서 아예 제거했습니다. 빨라지면서 안전해진 드문 사례입니다.

핸드셰이크에서 하는 일은 세 가지입니다.

- **인증** — 인증서로 "이 서버가 진짜 그 도메인이 맞는가" 확인
- **협상** — 어떤 암호 알고리즘을 쓸지 합의
- **키 교환** — 대칭키를 안전하게 공유 (이후 통신은 이 키로 암호화)

비대칭 암호(RSA, ECDSA)는 느려서 키 교환에만 쓰고,
실제 데이터는 빠른 대칭 암호(AES)로 처리합니다.

## 주니어가 자주 빠지는 함정

### 함정 1 — HTTP/2를 켜고도 1.1 시대의 최적화를 유지한다

HTTP/1.1에서는 요청 수를 줄이는 게 중요해서 이런 기법을 썼습니다.

```
- 이미지 여러 개를 한 장으로 합치기 (스프라이트)
- JS/CSS를 하나의 큰 파일로 번들링
- 도메인을 여러 개로 쪼개기 (샤딩)
```

HTTP/2에서는 **이게 오히려 손해**입니다.
요청은 이미 싼데, 파일 하나만 바뀌어도 큰 번들 전체를 다시 받아야 합니다.
도메인 샤딩은 연결을 쪼개서 멀티플렉싱 이득을 없앱니다.

백엔드 입장에서 직접 만질 일은 적지만, **"HTTP/2를 켜면 뭐가 달라지는가"를 알고 있어야
프론트엔드와 논의할 때 근거를 댈 수 있습니다.**

### 함정 2 — Nginx에서 HTTP/2를 켰다고 생각만 한다

```nginx
# 흔한 실수 - 옛 문법. Nginx 1.25부터 deprecated
listen 443 ssl http2;

# 권장 - 1.25 이상
listen 443 ssl;
http2 on;
```

그리고 **Nginx와 클라이언트 사이만 HTTP/2가 됩니다.**
Nginx에서 백엔드(gunicorn/uvicorn)로 가는 구간은 기본적으로 HTTP/1.1입니다.

```nginx
location / {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;      # 명시하지 않으면 1.0으로 간다
    proxy_set_header Connection "";   # keep-alive 유지
}
```

`proxy_http_version`을 안 적으면 Nginx는 백엔드에 **HTTP/1.0**으로 요청합니다.
1.0은 keep-alive가 기본이 아니라서, 2주차 화요일에 배운 연결 재사용 이득이 사라집니다.

확인 방법:

```bash
curl -I --http2 https://api.example.com/health
# 응답 첫 줄이 HTTP/2 200 이면 적용됨
```

### 함정 3 — TLS를 어디서 푸는지 모른다

```
[클라이언트] --HTTPS--> [로드밸런서] --HTTP--> [Nginx] --HTTP--> [앱]
                            ^ 여기서 TLS 종료
```

이 구성에서 앱이 보는 건 평문 HTTP입니다. 1주차 화요일 함정 4와 같은 이야기입니다.

```python
# Django - 프록시가 알려준 원래 스킴을 신뢰
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
SECURE_SSL_REDIRECT = True
```

이걸 빼먹으면 `request.is_secure()`가 항상 False가 되어,
HTTPS로 들어온 요청을 다시 HTTPS로 리디렉트하는 **무한 루프**가 생깁니다.

### 함정 4 — 인증서 만료를 사람이 챙긴다

TLS 인증서는 보통 90일(Let's Encrypt) 또는 1년입니다.
만료되면 **서비스가 통째로 접속 불가**가 됩니다. 코드는 멀쩡한데 아무도 못 들어옵니다.

```bash
# 만료일 확인
echo | openssl s_client -connect api.example.com:443 2>/dev/null \
  | openssl x509 -noout -dates
```

자동 갱신(certbot 등)을 걸어두고, **갱신 실패 시 알림**까지 설정해야 완성입니다.
자동 갱신만 걸고 알림을 안 걸면, 갱신이 조용히 실패했을 때 만료일에 알게 됩니다.

## 트레이드오프

```
HTTP/2로 올리면
  얻는 것: 멀티플렉싱으로 동시 요청 처리, 헤더 압축으로 대역폭 절약,
           연결 수 감소로 서버 부담 완화
  잃는 것: 구현 복잡도 증가, 디버깅이 어려움(바이너리라 눈으로 못 읽음),
           TCP 계층 HOL 블로킹은 그대로
  이득이 작은 상황: 요청 수가 적은 단순 API (멀티플렉싱 이득이 없음)

HTTP/3으로 올리면
  얻는 것: HOL 블로킹 완전 해결, 연결 수립 1 RTT, 연결 마이그레이션
  잃는 것: UDP를 막는 방화벽이 아직 있음, 운영 도구·모니터링 지원이 덜 성숙,
           구현체가 상대적으로 새것
  현실: 대부분 CDN이나 로드밸런서 레벨에서 켜고, 백엔드는 그대로 두는 구성이 많음

TLS를 쓰면
  얻는 것: 도청·변조 방지, 서버 신원 확인
  잃는 것: 핸드셰이크 왕복, 암복호화 CPU 비용
  현실: 하드웨어 가속과 TLS 1.3으로 비용이 많이 줄어서, 안 쓸 이유가 거의 없음
```

전체를 관통하는 관점 하나. **버전이 올라갈수록 병목이 아래 계층으로 내려갔습니다.**

```
HTTP/1.1 문제 -> 응용 계층에서 해결 (멀티플렉싱)  -> HTTP/2
HTTP/2 문제   -> 전송 계층을 교체 (TCP -> QUIC)   -> HTTP/3
```

1주차 화요일에 배운 계층 구조가 여기서 실제로 작동합니다.
**한 계층에서 못 푸는 문제는 아래 계층을 바꿔야 풀립니다.**
그리고 계층을 바꾸는 건 비싸기 때문에, 가능하면 위에서 해결하려고 20년 가까이 버틴 것입니다.

## 연결되는 CS 지식

- **TCP 3-way handshake와 keep-alive** — 2주차 화요일의 연결 재사용이 HTTP/2 멀티플렉싱, HTTP/3 0-RTT로 이어집니다. 같은 문제의식의 연속입니다.
- **OSI/TCP-IP 계층** — 1주차 화요일. 병목이 계층을 타고 내려간 과정이 오늘 내용입니다.
- **큐와 HOL 블로킹** — 줄 맨 앞이 막히면 전체가 막히는 건 큐 자료구조의 일반적 성질입니다. 4주차 목요일 주제와 만납니다.
- **압축 알고리즘** — HPACK은 허프만 부호화와 정적/동적 테이블을 씁니다.
- **대칭키와 비대칭키** — TLS가 둘을 조합하는 이유(비대칭은 안전하지만 느림)가 암호학의 기본 구도입니다.

## 다음 행동

```bash
# 이 서버가 어느 버전까지 지원하는지
curl -I --http2 https://api.example.com/health
curl -I --http3 https://api.example.com/health

# TLS 버전과 암호 스위트, 인증서 만료일
echo | openssl s_client -connect api.example.com:443 2>/dev/null | head -30
```

지금 운영 중인 서버에 실행해 보면 HTTP 버전과 TLS 버전이 바로 나옵니다.
아직 HTTP/1.1이라면 Nginx 설정 한 줄로 바꿀 수 있는지 확인해 보는 것도
오늘 내용을 실무로 옮기는 좋은 출발점입니다.
