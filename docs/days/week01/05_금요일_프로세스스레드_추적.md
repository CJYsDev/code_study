# 요청 한 건은 어느 프로세스, 어느 스레드가 처리하는가

1일 1CS / 1주차 금요일 / 통합 과제
코드: [`lab/week01_fri_process_thread_lab.py`](../../../lab/week01_fri_process_thread_lab.py)

이번 주에 배운 네 가지를 요청 한 건 위에서 확인한다.

| 주제 | 이 과제에서 확인하는 것 |
|---|---|
| 프로세스와 스레드 (월) | 요청이 어느 PID·TID에서 처리되는가 |
| HTTP 요청의 여정 (화) | Nginx 뒤에서 앱이 실제로 무엇을 받는가 |
| 트랜잭션과 ACID (수) | 프로세스가 나뉘면 왜 상태 공유가 안 되는가 |
| 시간복잡도 (목) | worker를 늘리면 처리량이 어떻게 변하는가 |

## 1단계 — 요청 처리 주체를 찍는 앱 만들기

`main.py`

```python
import os
import threading
import time

from fastapi import FastAPI

app = FastAPI()

# 프로세스마다 자기 사본을 갖는 전역 상태 (3단계에서 관찰)
request_count = 0


def identity() -> dict:
    return {
        "pid": os.getpid(),
        "tid": threading.get_ident(),
        "thread_name": threading.current_thread().name,
    }


@app.get("/who")
def who():
    """누가 이 요청을 처리했는가"""
    return identity()


@app.get("/count")
def count():
    """전역 변수는 프로세스 간에 공유되지 않는다"""
    global request_count
    request_count += 1
    return {"count": request_count, **identity()}


@app.get("/slow")
def slow():
    """IO 대기 - 기다리는 동안 CPU를 놓는다"""
    time.sleep(2)
    return {"kind": "io", **identity()}


@app.get("/heavy")
def heavy():
    """CPU 작업 - GIL을 붙잡는다"""
    total = 0
    for i in range(20_000_000):
        total += i
    return {"kind": "cpu", "total": total, **identity()}
```

## 2단계 — worker 1개, 스레드 1개

```bash
gunicorn main:app -k uvicorn.workers.UvicornWorker --workers 1
```

다른 터미널에서:

```bash
for i in $(seq 1 5); do curl -s localhost:8000/who; echo; done
```

**관찰 포인트**

- `pid`가 전부 같다 → 프로세스 하나
- `tid`도 전부 같다 → 그 프로세스 안의 이벤트 루프 스레드 하나

기록해 둔다.

| 항목 | 값 |
|---|---|
| 서로 다른 pid 개수 | |
| 서로 다른 tid 개수 | |

## 3단계 — worker 4개

```bash
gunicorn main:app -k uvicorn.workers.UvicornWorker --workers 4
```

```bash
for i in $(seq 1 12); do curl -s localhost:8000/who; echo; done
```

**관찰 포인트**

- `pid`가 여러 개 나온다. 최대 4종류
- 요청이 어느 worker로 갈지는 정해져 있지 않다

이제 전역 변수를 확인한다.

```bash
for i in $(seq 1 10); do curl -s localhost:8000/count; echo; done
```

**여기가 이번 과제의 핵심입니다.**

`count`가 1, 2, 3... 으로 늘지 않고 **들쭉날쭉하게 나옵니다.**
1이 여러 번 나오고, 2가 여러 번 나옵니다.

worker 4개가 각자 자기 `request_count`를 갖고 있기 때문입니다.
같은 코드에서 나온 변수인데 **메모리 공간이 다르므로 서로를 모릅니다.**

월요일에 배운 "프로세스는 메모리가 독립되어 있다"가 눈앞에서 확인되는 순간입니다.
그리고 이게 인메모리 캐시, 로그인 세션, 스케줄러 등록이
운영 환경에서만 깨지는 이유이기도 합니다.

| 항목 | 값 |
|---|---|
| 10번 호출했을 때 마지막 count 값 | |
| 서로 다른 pid 개수 | |

## 4단계 — 프로세스로도 공유되는 저장소로 바꿔보기

Redis가 있다면 `/count`를 이렇게 바꿔본다.

```python
# pip install redis
import redis

r = redis.Redis(decode_responses=True)


@app.get("/count-shared")
def count_shared():
    value = r.incr("request_count")
    return {"count": value, **identity()}
```

```bash
for i in $(seq 1 10); do curl -s localhost:8000/count-shared; echo; done
```

이번에는 pid가 달라도 **count가 1부터 10까지 정확히 올라갑니다.**

여기서 "Redis가 왜 필요한가"가 답해집니다.
빠른 캐시라서가 아니라, **프로세스 밖에 있는 공용 공간**이기 때문입니다.
worker가 여러 개인 순간부터 상태는 프로세스 밖에 두어야 합니다.

## 5단계 — 스레드를 추가하면 무엇이 달라지나

```bash
gunicorn main:app --workers 2 --threads 4
```

(uvicorn worker 대신 기본 sync worker로 실행)

```bash
for i in $(seq 1 20); do curl -s localhost:8000/who; echo; done
```

**관찰 포인트**

- `pid`는 2종류
- 같은 pid 안에서 `tid`가 여러 개 나온다

프로세스와 스레드가 어떻게 겹쳐 쌓이는지가 보입니다.
동시에 붙잡을 수 있는 요청 수는 2 × 4 = 8입니다.

## 6단계 — IO 작업과 CPU 작업의 차이

**IO 작업 (`/slow`, 2초 대기)**

```bash
gunicorn main:app --workers 1 --threads 4

time (for i in $(seq 1 4); do curl -s localhost:8000/slow & done; wait)
```

4개를 동시에 보냈는데 **총 2초 근처**에서 끝납니다.
대기 중에는 GIL을 놓으므로 스레드들이 겹쳐서 진행합니다.

**CPU 작업 (`/heavy`)**

```bash
time (for i in $(seq 1 4); do curl -s localhost:8000/heavy & done; wait)
```

이번에는 시간이 **거의 4배**로 늘어납니다.
GIL 때문에 한 번에 하나씩만 실행되기 때문입니다.

worker를 4개로 바꿔서 다시 해봅니다.

```bash
gunicorn main:app --workers 4

time (for i in $(seq 1 4); do curl -s localhost:8000/heavy & done; wait)
```

이번에는 짧아집니다. 프로세스마다 GIL이 따로 있기 때문입니다.

| 구성 | `/slow` 4건 | `/heavy` 4건 |
|---|---|---|
| workers 1, threads 1 | | |
| workers 1, threads 4 | | |
| workers 4 | | |

## 정리

표를 다 채웠다면 다음 세 문장을 자기 말로 설명할 수 있어야 한다.

1. worker를 늘리면 전역 변수가 왜 어긋나는가
2. IO 작업은 스레드로 해결되는데 CPU 작업은 왜 안 되는가
3. 그래서 내 서비스의 worker 수는 무엇을 기준으로 정해야 하는가

3번에 대한 답이 애매하다면, 그건 **아직 내 서비스가 CPU를 쓰느라 바쁜지
기다리느라 바쁜지 모른다**는 뜻입니다. 그걸 재는 게 2주차 금요일 실험입니다.
