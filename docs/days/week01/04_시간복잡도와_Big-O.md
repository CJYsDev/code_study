# 시간복잡도와 Big-O — 무엇을 재는 기준인가

1일 1CS / 1주차 목요일 / 자료구조·알고리즘
티어: C (7섹션 전부)

---

## 한 줄 요약

Big-O는 코드가 **몇 초 걸리는지**를 재는 게 아니라,
**입력이 커질 때 비용이 어떤 모양으로 늘어나는지**를 표시하는 기호입니다.

---

## 이게 없으면 생기는 문제

### 문제 1 — 로컬에서는 절대 안 터진다

장비 목록에 각 장비의 최신 측정값을 붙여서 내려주는 API가 있다고 합시다.

```python
devices = Device.objects.all()
result = []
for device in devices:
    latest = Measurement.objects.filter(device=device).latest("created_at")
    result.append({"device": device.name, "value": latest.value})
```

개발 DB에 장비가 10대일 때는 쿼리가 11번 나가고 0.05초에 끝납니다. 아무 문제 없어 보입니다.
운영에 장비가 5,000대 있으면 쿼리가 5,001번 나갑니다.
쿼리 하나가 2ms라 해도 **10초**입니다. 타임아웃이 납니다.

느려진 게 아닙니다. **처음부터 O(n)이었는데 n이 작아서 안 보였을 뿐입니다.**
Big-O는 "지금 빠른가"가 아니라 "10배 늘어나면 어떻게 되는가"를 미리 보는 도구입니다.

### 문제 2 — 성능을 논의할 공통 언어가 없다

"제 노트북에서 0.3초 나왔어요"는 근거가 되기 어렵습니다.
CPU가 다르고, 데이터가 다르고, 캐시 상태가 다릅니다. 다른 사람이 재현할 수 없습니다.

반면 "이건 O(n²)이고 저건 O(n log n)입니다"는 기계와 무관하게 성립합니다.
코드 리뷰에서 성능 이야기를 할 때 서로 같은 것을 보고 있게 만드는 **공용 단위**입니다.

---

## 비유

**책에서 단어 하나를 찾는 방법입니다.**

- 1페이지부터 한 장씩 넘기며 찾기 → 책이 2배 두꺼워지면 시간도 2배. `O(n)`
- 뒤쪽 색인(index)을 펴서 찾기 → 책이 2배가 되어도 몇 장만 더 넘기면 됨. `O(log n)`

핵심은 **"두꺼워졌을 때 얼마나 더 힘들어지는가"**입니다.
100페이지짜리 책에서는 두 방법의 차이가 거의 없습니다.
10,000페이지짜리 사전에서는 차이가 결정적입니다.

단, 이 비유가 놓치는 부분이 둘 있습니다.
색인을 **만드는** 비용이 따로 든다는 점(3주차 인덱스 주제에서 다시 나옵니다),
그리고 책이 얇으면 색인을 펴는 수고가 오히려 손해라는 점입니다.
Big-O는 이 두 가지를 보여주지 않습니다.

## 실제로 어떻게 동작하는가

### 규칙 두 개면 끝납니다

```python
def process(items):          # 입력 크기 n
    total = 0                # 1번    -> 상수
    for a in items:          # n번
        for b in items:      #   n번  -> n * n
            total += a * b
    print(total)             # 1번    -> 상수

# 정확히 세면: n² + 2
# Big-O로 쓰면: O(n²)
```

- **상수는 버린다** — `2n`도 `100n`도 전부 `O(n)`. n이 커지면 배수는 의미가 없어짐
- **낮은 차수는 버린다** — `n² + n`은 `O(n²)`. n이 커지면 n²가 전부를 지배함

버리는 이유는 Big-O가 **모양**을 보는 기호이기 때문입니다.
"2배 늘면 4배 느려지는 모양"이 n²이고, 계수가 얼마인지는 이 질문의 답과 무관합니다.

### 자주 나오는 복잡도

n = 1,000일 때 대략적인 연산 횟수를 같이 적었습니다.

| 복잡도 | 이름 | n=1,000일 때 | 대표 예시 |
|---|---|---|---|
| O(1) | 상수 | 1 | dict 조회, list 인덱싱 |
| O(log n) | 로그 | 약 10 | 이진 탐색, B-tree 인덱스 조회 |
| O(n) | 선형 | 1,000 | 리스트 전체 순회, `in` 리스트 검사 |
| O(n log n) | 선형 로그 | 약 10,000 | 정렬 (`sorted`, `list.sort`) |
| O(n²) | 이차 | 1,000,000 | 이중 루프, 모든 쌍 비교 |
| O(2ⁿ) | 지수 | 계산 불가 | 부분집합 전체 탐색 |

O(n)에서 O(n²)로 가는 순간 **세 자리가 뜁니다.**
실무에서 성능 문제의 대부분은 여기서 발생합니다. 그 아래 구간의 차이는 보통 문제가 안 됩니다.

### Python 자료구조별 주요 연산

이 표는 외워둘 만합니다. 실전에서 제일 자주 쓰입니다.

| 연산 | list | dict / set |
|---|---|---|
| 값이 있는지 확인 (`x in c`) | O(n) | O(1) |
| 인덱스/키로 접근 | O(1) | O(1) |
| 끝에 추가 | O(1) | O(1) |
| 맨 앞에 추가/삭제 | O(n) | 해당 없음 |
| 값으로 삭제 | O(n) | O(1) |

dict와 set이 O(1)인 이유는 해시테이블이기 때문입니다. (3주차 목요일 주제)

### 최선·평균·최악, 그리고 공간

Big-O는 보통 **최악의 경우**를 말합니다.
운이 좋아 첫 번째에 찾는 경우가 아니라, 끝까지 못 찾는 경우를 기준으로 잡습니다.
서비스 안정성은 최악의 경우가 결정하기 때문입니다.

같은 방식으로 메모리도 잽니다. 이건 **공간복잡도**입니다.
시간을 줄이려고 캐시를 만들면 공간이 늘어납니다. 이 맞바꿈이 뒤에서 계속 나옵니다.

## 주니어가 자주 빠지는 함정

### 함정 1 — 리스트에 `in`을 쓴다

```python
# 흔한 실수 - allowed_ids가 리스트면 검사 한 번이 O(n)
allowed_ids = [d.id for d in Device.objects.filter(is_active=True)]

for measurement in measurements:
    if measurement.device_id in allowed_ids:   # 여기가 O(n)
        process(measurement)
# 전체: O(n * m) -> 사실상 O(n²)

# 권장 - set으로 바꾸면 검사가 O(1)
allowed_ids = {d.id for d in Device.objects.filter(is_active=True)}

for measurement in measurements:
    if measurement.device_id in allowed_ids:   # O(1)
        process(measurement)
# 전체: O(n)
```

대괄호를 중괄호로 바꾸는 **한 글자짜리 수정**인데 복잡도가 한 단계 내려갑니다.
"루프 안에서 `in` 리스트"를 보면 반사적으로 의심하는 습관을 들여두면 좋습니다.

### 함정 2 — 리스트 앞쪽을 건드린다

```python
# 흔한 실수 - pop(0)은 뒤의 원소를 전부 한 칸씩 당긴다. O(n)
queue = list(range(100000))
while queue:
    item = queue.pop(0)      # 매번 O(n) -> 전체 O(n²)

# 권장 - deque는 양쪽 끝이 O(1)
from collections import deque

queue = deque(range(100000))
while queue:
    item = queue.popleft()   # O(1) -> 전체 O(n)
```

`insert(0, x)`도 같습니다. 리스트는 연속된 메모리라 앞을 건드리면 전부 밀어야 합니다.
왜 그런지는 2주차 목요일 "배열 vs 연결리스트"에서 이어집니다.

### 함정 3 — 루프 안에서 쿼리를 날린다 (N+1)

맨 위에서 본 예시입니다. 이게 특히 위험한 이유는 **상수가 아주 크기** 때문입니다.

```python
# 흔한 실수 - 쿼리 N+1번
for device in Device.objects.all():
    print(device.location.name)      # 접근할 때마다 추가 쿼리

# 권장 - 쿼리 1~2번
for device in Device.objects.select_related("location"):
    print(device.location.name)
```

둘 다 표기상으로는 O(n)입니다. 하지만 앞의 것은 단위가 **네트워크 왕복**이고
뒤의 것은 **메모리 접근**입니다. 실제 차이는 수천 배가 납니다.

DB가 걸린 코드에서는 연산 횟수가 아니라 **쿼리 횟수를 n으로 세는 습관**이 필요합니다.
Django에서는 `django-debug-toolbar`나 `connection.queries`로 몇 번 나갔는지 바로 확인할 수 있습니다.

### 함정 4 — Big-O만 보고 상수를 무시한다

```python
# n이 20 정도라면, 이 O(n²) 코드가
for a in items:
    for b in items:
        compare(a, b)

# 인덱스를 만들어 조회하는 O(n) 코드보다 실제로 빠를 수 있다
```

Big-O는 **n이 충분히 클 때**의 이야기입니다.
n이 작으면 상수와 준비 비용이 전부를 좌우합니다.

정렬을 예로 들면, 대부분의 표준 라이브러리는 배열이 작을 때 O(n²)인 삽입 정렬로 전환합니다.
O(n log n) 알고리즘의 오버헤드가 더 크기 때문입니다.
Python의 `sorted`도 내부적으로 이렇게 동작합니다.

**"복잡도가 낮다 = 항상 빠르다"가 아닙니다.** n의 실제 크기를 먼저 확인해야 합니다.

## 트레이드오프

```
Big-O로 사고하면
  얻는 것: 기계·언어와 무관한 비교 기준, 데이터가 커졌을 때의 거동을 미리 예측,
           코드 리뷰에서 성능을 말할 공용 언어
  잃는 것: 상수 배수를 못 봄, 메모리 접근 패턴/캐시 효율을 못 봄,
           네트워크 왕복 같은 단위 차이를 못 봄
  손해인 상황: n이 항상 작다고 확신할 수 있는 코드를 미리 최적화하는 경우
              -> 읽기 어려워지기만 하고 얻는 게 없음
```

실무에서의 순서는 이렇습니다.

1. Big-O로 **모양이 잘못된 곳**을 먼저 찾는다 (O(n²), N+1 같은 것)
2. 그걸 고친 뒤에도 느리면 **실제로 측정**한다 (프로파일러, `EXPLAIN`)
3. 상수를 줄이는 최적화는 그다음이다

Big-O는 1단계 도구입니다. 2단계를 대체하지 못하고, 2단계도 1단계를 대체하지 못합니다.

시간-공간 맞바꿈도 여기서 나옵니다.
리스트를 set으로 바꾸면 조회는 O(n)에서 O(1)이 되지만 메모리를 더 씁니다.
캐시, 인덱스, 반정규화가 전부 같은 형태의 거래입니다.

## 연결되는 CS 지식

- **해시테이블** — dict와 set이 어떻게 O(1)을 만드는지, 그리고 그게 항상 O(1)은 아닌 이유를 봅니다. (3주차 목요일 주제)
- **인덱스와 B-tree** — DB에서 `O(n)` 전체 스캔을 `O(log n)` 조회로 바꾸는 장치입니다. 오늘의 색인 비유가 그대로 이어집니다. (2주차 수요일 주제)
- **배열 vs 연결리스트** — 함정 2의 `pop(0)`이 왜 O(n)인지가 여기서 설명됩니다. (2주차 목요일 주제)
- **`EXPLAIN`과 실행 계획** — Seq Scan은 O(n), Index Scan은 O(log n)입니다. 3주차 금요일 통합 과제에서 직접 확인합니다.
- **정규화와 반정규화** — 조인 횟수를 줄여 조회 복잡도를 낮추는 대신 저장 공간과 정합성을 내주는 거래입니다.
