# OSI 계층과 HTTP 요청 — 한 건은 어떤 계층을 거쳐 가는가

1일 1CS / 1주차 화요일 / 네트워크
티어: C (7섹션 전부)

---

## 한 줄 요약

계층 모델은 외우는 지식이 아니라, **"네트워크가 안 될 때 어디부터 봐야 하는지"** 범위를 좁혀주는 지도입니다.

---

## 이게 없으면 생기는 문제

### 만드는 쪽의 고통

계층 구분이 없다면, API 하나를 짜는데 전기 신호를 어떻게 실어 보낼지까지 알아야 합니다.
사용자가 WiFi를 쓰는지 LTE를 쓰는지에 따라 애플리케이션 코드를 다시 짜야 합니다.
"HTTP를 안다"는 말이 "이더넷 프레임 포맷을 안다"와 같은 뜻이 되어버립니다.

계층은 이걸 잘라냅니다. HTTP를 만드는 사람은 **바로 아래층에게 넘긴다**는 것만 알면 됩니다.

### 고치는 쪽의 고통 (이쪽이 더 큽니다)

실무에서 훨씬 자주 겪는 건 이겁니다.

> "API가 안 돼요"

원인 후보가 이만큼 있습니다.

- 도메인이 잘못된 IP를 가리킴
- 보안그룹/방화벽이 포트를 막음
- TLS 인증서 만료
- Nginx 설정이 백엔드를 못 찾음
- gunicorn worker가 전부 물려서 응답을 못 함
- 애플리케이션 코드에서 예외 발생

계층 개념이 없으면 이 목록을 위에서부터 하나씩 찍어봅니다.
계층 개념이 있으면 **아래에서 위로 잘라 올라가며** 후보를 절반씩 줄입니다.

```bash
ping api.example.com          # 여기서 막히면 -> DNS 또는 3계층
telnet api.example.com 443    # 여기서 막히면 -> 방화벽 또는 4계층
curl -v https://api.example.com/health   # 여기서 막히면 -> TLS 또는 7계층
```

계층은 **문제를 이분 탐색하기 위한 눈금**입니다. 이게 계층을 배우는 진짜 이유입니다.

---

## 비유

**국제 우편입니다.**

편지 내용을 쓰고(HTTP), 봉투에 넣어 받는 사람 이름을 적고(TCP 포트),
그 봉투를 다시 국제 우편 상자에 넣어 국가와 도시를 적고(IP 주소),
그 상자를 트럭과 비행기가 실어 나릅니다(물리 계층).

핵심은 **각 단계가 아래 단계의 사정을 모른다**는 점입니다.
편지를 쓴 사람은 비행기가 뜨는지 배가 뜨는지 신경 쓰지 않습니다.
비행기 조종사는 편지 내용을 읽지 않습니다.

단, 이 비유가 맞지 않는 부분: 실제 우체국은 봉투를 뜯지 않지만,
네트워크에서는 중간 장비가 봉투를 뜯어봅니다.
로드밸런서, 리버스 프록시, API 게이트웨이는 7계층 내용(URL, 헤더)을 읽고 판단합니다.
이게 나중에 "TLS를 어디서 푸는가" 문제로 이어집니다.

## 실제로 어떻게 동작하는가

### OSI 7계층과 TCP/IP 4계층

OSI는 이론 모델이고, 실제 인터넷이 돌아가는 방식은 TCP/IP 쪽에 가깝습니다.
면접에서는 OSI를 묻지만, 장애를 잡을 때 쓰는 건 아래 오른쪽입니다.

| OSI | TCP/IP | 실제로 뭐가 여기 있나 |
|---|---|---|
| 7 응용 / 6 표현 / 5 세션 | 응용 | HTTP, DNS, TLS, WebSocket |
| 4 전송 | 전송 | TCP, UDP — 포트 번호, 신뢰성 |
| 3 네트워크 | 인터넷 | IP, ICMP(ping) — 주소와 라우팅 |
| 2 데이터링크 / 1 물리 | 네트워크 접근 | 이더넷, WiFi, MAC 주소 |

실무에서 압도적으로 자주 보는 건 3, 4, 7계층 셋뿐입니다.
5·6계층은 현대 스택에서 사실상 7계층에 흡수되었습니다.

### 캡슐화 — 데이터가 내려가면서 옷을 입는다

```
[ HTTP 요청 본문 ]                                    (7계층에서 출발)
[ TCP 헤더 | HTTP 요청 본문 ]                          (출발지·목적지 포트가 붙음)
[ IP 헤더 | TCP 헤더 | HTTP 요청 본문 ]                (출발지·목적지 IP가 붙음)
[ 프레임 헤더 | IP 헤더 | TCP 헤더 | HTTP 본문 | FCS ] (MAC 주소가 붙음)
```

받는 쪽은 이걸 정확히 **역순으로 벗깁니다.**
그래서 각 계층은 "같은 계층의 상대"와 대화하는 것처럼 동작합니다.

### 요청 한 건의 전체 여정

`https://api.example.com/sensors` 를 호출했다고 합시다.

**1단계 — URL 파싱**
스킴(https), 호스트(api.example.com), 경로(/sensors)를 분리합니다. 포트는 생략 시 443.

**2단계 — DNS 조회 (7계층)**
도메인 이름을 IP 주소로 바꿉니다.
브라우저 캐시 → OS 캐시 → 로컬 resolver → 루트 서버 → TLD 서버 → 권한 서버 순으로 찾습니다.
캐시가 있으면 대부분 첫 단계에서 끝납니다. 이 단계가 실패하면 `Name or service not known`입니다.

**3단계 — TCP 연결 (4계층)**

```
클라이언트 --- SYN ------------> 서버
클라이언트 <-- SYN + ACK ------- 서버
클라이언트 --- ACK ------------> 서버
```

3번 왕복해야 데이터를 보낼 수 있습니다. 왕복 지연이 100ms면 여기서만 150ms를 씁니다.
이 단계에서 막히면 방화벽이나 보안그룹을 의심합니다. (자세한 내용은 2주차 화요일 주제)

**4단계 — TLS 핸드셰이크 (https인 경우)**
인증서 검증, 암호 스위트 협상, 세션 키 교환.
TLS 1.2는 2왕복, TLS 1.3은 1왕복입니다. 인증서가 만료되면 여기서 끊깁니다.

**5단계 — HTTP 요청 전송 (7계층)**

```http
GET /sensors HTTP/1.1
Host: api.example.com
Accept: application/json
```

`Host` 헤더가 중요합니다. 서버 하나에 여러 도메인이 붙어 있을 때
어느 서비스로 보낼지 판단하는 근거가 이 헤더입니다.

**6단계 — 서버 내부**

```
Nginx (리버스 프록시)
  -> TLS 종료, 정적 파일 처리, 라우팅
  -> gunicorn / uvicorn (WSGI / ASGI 서버)
      -> Django / FastAPI 애플리케이션
          -> DB 조회
```

여기서 어제 주제와 만납니다. Nginx가 넘긴 요청을 **어느 프로세스, 어느 스레드**가 받는지가
바로 어제 본 내용입니다.

**7단계 — 응답이 역순으로 돌아옴**

**8단계 — 연결 유지 또는 종료**
HTTP/1.1의 keep-alive 덕분에 보통 연결을 끊지 않고 재사용합니다.
매 요청마다 3단계·4단계를 다시 하지 않아도 되므로 체감 차이가 큽니다.

## 주니어가 자주 빠지는 함정

### 함정 1 — 바인딩 주소를 127.0.0.1로 둔다

컨테이너나 EC2에 올렸는데 밖에서 접속이 안 되는 전형적인 원인입니다.

```python
# 흔한 실수 - 자기 자신에게서만 접근 가능
uvicorn.run(app, host="127.0.0.1", port=8000)

# 권장 - 모든 인터페이스에서 수신
uvicorn.run(app, host="0.0.0.0", port=8000)
```

`127.0.0.1`은 "이 기계 내부"만 가리킵니다. 컨테이너 안에서 이렇게 띄우면
호스트에서 포트를 매핑해도 닿지 않습니다.
Django도 마찬가지로 `runserver 0.0.0.0:8000`이어야 합니다.

### 함정 2 — CORS 에러를 네트워크 장애로 오해한다

```
Access to fetch at 'https://api.example.com' from origin 'http://localhost:3000'
has been blocked by CORS policy
```

이건 **요청이 서버에 잘 도착했고 응답도 잘 왔다**는 뜻입니다.
브라우저가 응답을 JS에게 넘겨주지 않고 막은 것뿐입니다.
서버 로그를 보면 요청이 200으로 찍혀 있습니다.

```python
# 권장 - 서버가 응답 헤더로 "이 출처는 허용한다"고 알려줘야 한다
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],
    allow_credentials=True,
)
```

`curl`로는 되는데 브라우저에서만 안 된다면 거의 항상 CORS입니다.
curl에는 출처 개념이 없어서 정책을 적용하지 않기 때문입니다.

### 함정 3 — 5xx를 다 같은 것으로 본다

숫자마다 **끊긴 계층이 다릅니다.**

| 코드 | 누가 냈나 | 무슨 뜻인가 | 어디를 보나 |
|---|---|---|---|
| 500 | 애플리케이션 | 코드에서 예외 발생 | Django/FastAPI 로그 |
| 502 | Nginx | 백엔드에 붙었는데 응답이 이상함 | worker가 죽었는지 |
| 503 | Nginx 또는 LB | 백엔드가 아예 없음 | 프로세스가 떠 있는지 |
| 504 | Nginx | 백엔드가 제한 시간 안에 답을 못 함 | 느린 쿼리, worker 부족 |

502와 504를 구분하면 "앱이 죽었나"와 "앱이 느린가"가 바로 갈립니다.
504가 계속 뜬다면 어제 본 worker 수 문제일 가능성이 높습니다.

### 함정 4 — 프록시 뒤에서 클라이언트 정보를 잘못 읽는다

Nginx가 TLS를 풀고 백엔드에는 평문 HTTP로 넘기는 구성이 일반적입니다.
이때 애플리케이션이 보는 값은 실제 클라이언트의 값이 아닙니다.

```python
# 흔한 실수 - 프록시 뒤에서는 항상 "http", 항상 프록시의 IP가 나온다
scheme = request.url.scheme          # 실제로는 https였는데 http로 보임
client_ip = request.client.host      # 실제 사용자가 아니라 Nginx의 IP

# 권장 - 프록시가 넘겨준 헤더를 신뢰하도록 설정한다
# Nginx
#   proxy_set_header X-Forwarded-Proto $scheme;
#   proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

# Django settings.py
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
```

이걸 놓치면 리디렉션 무한 루프가 생기거나, 접속 로그의 IP가 전부 같아집니다.
단, 이 헤더는 클라이언트가 위조할 수 있으므로 **신뢰할 수 있는 프록시 뒤에서만** 켜야 합니다.

## 트레이드오프

```
계층 구조를 쓰면
  얻는 것: 계층별 독립 교체(WiFi -> LTE 전환에 앱 수정 불필요),
           장애 범위를 계층 단위로 좁힐 수 있음, 표준화로 상호 운용 가능
  잃는 것: 헤더 중첩으로 인한 오버헤드, 계층을 가로지르는 최적화가 어려움,
           추상화 누수(TCP 재전송이 애플리케이션 지연으로 드러남)
  손해인 상황: 초저지연이 절대 조건인 경우 (고빈도 거래, 실시간 게임)
              -> 계층을 우회하는 kernel bypass 같은 기법을 씀
```

한 가지 더. **OSI 7계층을 순서대로 외우는 것 자체는 실무 효용이 거의 없습니다.**
7계층 암기에 시간을 쓰기보다, 3·4·7계층 각각에서 무엇이 깨질 수 있는지를
증상과 짝지어 기억하는 편이 훨씬 남습니다.

## 연결되는 CS 지식

- **TCP 3-way handshake와 keep-alive** — 3단계에서 왕복이 왜 3번인지, 왜 연결 재사용이 그렇게 큰 차이를 내는지로 이어집니다. (2주차 화요일 주제)
- **소켓과 파일 디스크립터** — 어제 본 프로세스·스레드가 네트워크 연결을 어떻게 붙잡고 있는지 연결됩니다. `Too many open files` 에러의 정체이기도 합니다.
- **추상화와 캡슐화** — 계층 모델은 소프트웨어 설계 원칙이 네트워크에 그대로 적용된 사례입니다.
- **큐와 버퍼** — 각 계층 사이에는 버퍼가 있고, 이게 넘치면 패킷이 버려집니다. 목요일의 스택·큐 주제와 만납니다.
