# 해시테이블 — 어떻게 비교 없이 찾는가

1일 1CS / 3주차 목요일 / 자료구조·알고리즘
티어: C (7섹션 전부)

---

## 한 줄 요약

해시테이블은 **값 자체를 위치로 바꿔버려서** 찾는 과정을 없앤 자료구조입니다.
비교를 한 번도 안 하기 때문에 `O(1)`이 나옵니다.

---

## 이게 없으면 생기는 문제

### 문제 1 — 찾으려면 비교해야 한다

지금까지 배운 자료구조는 전부 **비교**로 찾았습니다.

| 자료구조 | 찾는 방법 | 복잡도 |
|---|---|---|
| 배열/연결리스트 | 처음부터 하나씩 비교 | O(n) |
| B-tree | 정렬을 이용해 절반씩 좁힘 | O(log n) |

`O(log n)`도 충분히 빠릅니다. 하지만 여전히 **비교를 몇 번은 해야 합니다.**
100만 건이면 약 20번, 10억 건이면 약 30번.

그런데 이런 질문이 남습니다.

> 비교를 아예 안 하고 바로 갈 수는 없나?

배열은 이미 그게 됩니다. `arr[15]`는 주소를 계산해서 한 번에 갑니다.
문제는 **인덱스가 정수여야 한다**는 것입니다.

`users["jaeyong@example.com"]`처럼 문자열로 찾고 싶다면?
이메일을 정수로 바꿀 수만 있으면 배열처럼 쓸 수 있습니다.
그 변환기가 **해시 함수**입니다.

### 문제 2 — 실무의 조회 대부분이 "이 키에 해당하는 값"이다

- 세션 ID로 로그인 정보 찾기
- 캐시 키로 값 찾기
- 사용자 ID로 권한 확인
- 요청 경로로 처리할 함수 찾기 (라우팅)

전부 "정확히 일치하는 하나"를 찾는 조회입니다. 범위도 정렬도 필요 없습니다.
이런 조회만 놓고 보면 `O(log n)`도 낭비입니다.

Redis가 왜 그렇게 빠른지, Python `dict`가 왜 그렇게 자주 쓰이는지,
DB 조인이 내부적으로 어떻게 처리되는지가 전부 이 자료구조 하나로 설명됩니다.

---

## 비유

**옷장 서랍입니다.**

옷을 아무 서랍에나 넣으면, 찾을 때 서랍을 다 열어봐야 합니다.
대신 규칙을 정합니다. "양말은 1번, 셔츠는 2번, 바지는 3번."

이제 셔츠를 찾을 때 **2번 서랍만 엽니다.** 다른 서랍은 쳐다보지도 않습니다.
서랍이 100개로 늘어나도 셔츠는 여전히 2번 서랍에 있습니다.
**물건이 늘어나도 찾는 시간이 안 늘어납니다.**

여기서 문제가 하나 생깁니다.
"셔츠"와 "스카프"가 둘 다 2번 서랍으로 배정되면 어떻게 할까요?
2번 서랍을 열고 **그 안에서는 하나씩 봐야 합니다.** 이게 충돌(collision)입니다.

단, 이 비유가 놓치는 부분: 실제 해시 함수는 "양말 → 1번"처럼 의미 기반이 아닙니다.
값을 뒤섞어서 나온 숫자를 쓰기 때문에, **비슷한 키가 전혀 다른 자리**로 갑니다.
`"user_1"`과 `"user_2"`가 서랍 3번과 서랍 87번에 들어가는 식입니다.
이 성질이 뒤에 나올 "정렬이 안 된다"는 한계의 원인입니다.

---

## 실제로 어떻게 동작하는가

### 기본 구조

```
키 "jaeyong@example.com"
        |
        v  해시 함수
   hash = 8374652918...
        |
        v  % 배열 크기(8)
   인덱스 = 6
        |
        v
버킷:  [0][1][2][3][4][5][6][7]
                          ^
                     여기에 저장
```

**해시테이블은 배열 위에 얹혀 있습니다.**
2주차 목요일에 배운 배열의 `O(1)` 인덱스 접근을 그대로 활용합니다.
해시 함수는 "임의의 키를 배열 인덱스로 바꿔주는 변환기"일 뿐입니다.

### 좋은 해시 함수의 조건

- **고르게 퍼뜨린다** — 특정 자리에 몰리면 충돌이 늘어남
- **빠르다** — 조회마다 실행되므로 느리면 의미가 없음
- **같은 키는 항상 같은 값** — 당연하지만 핵심

### 충돌 처리

서로 다른 키가 같은 인덱스로 가는 건 **피할 수 없습니다.**
키의 가짓수는 무한한데 배열 칸은 유한하기 때문입니다 (비둘기집 원리).

**방법 1 — 체이닝**

한 칸에 여러 개를 매달아 둡니다.

```
[0] -> None
[1] -> ("a", 1) -> ("k", 9)      <- 충돌. 연결리스트로 이어짐
[2] -> ("c", 3)
```

2주차 목요일에 배운 연결리스트가 여기서 쓰입니다.
**배열과 연결리스트가 함께 쓰이는 대표 사례**입니다.

**방법 2 — 개방 주소법**

자리가 차 있으면 **다음 빈 칸**으로 갑니다.

```
인덱스 3이 차 있음 -> 4를 확인 -> 4도 차 있음 -> 5에 저장
```

Python의 `dict`가 이 방식입니다. 연결리스트를 안 만들어서 메모리를 아끼고,
값들이 배열 안에 모여 있어 **캐시 지역성**도 좋습니다.
(2주차 목요일에 배운 그 지역성입니다)

### 적재율과 리사이징

```
적재율 = 저장된 항목 수 / 배열 크기
```

이 값이 커질수록 충돌이 잦아지고, 조회가 `O(1)`에서 멀어집니다.
그래서 일정 기준(Python은 약 2/3)을 넘으면 **배열을 키우고 전부 다시 배치**합니다.

```
크기 8, 항목 6개 -> 기준 초과
-> 크기 16짜리 배열을 새로 만들고
-> 기존 항목을 전부 다시 해싱해서 옮김   <- O(n)
```

이 순간은 `O(n)`입니다. 하지만 자주 일어나지 않으므로
평균을 내면 여전히 `O(1)`입니다. **분할상환 O(1)**입니다.
2주차 목요일에 리스트 `append`에서 본 것과 같은 구조입니다.

### 최악의 경우는 O(n)

모든 키가 같은 인덱스로 간다면, 결국 하나씩 다 봐야 합니다.

| 경우 | 복잡도 |
|---|---|
| 평균 | O(1) |
| 최악 | O(n) |

`O(1)`은 **평균이지 보장이 아닙니다.**
악의적으로 충돌을 유도하는 입력을 넣으면 성능을 무너뜨릴 수 있습니다(HashDoS).
그래서 Python은 실행할 때마다 해시 시드를 무작위로 바꿉니다.

### Python에서

| 타입 | 실체 |
|---|---|
| `dict` | 해시테이블 (키 → 값) |
| `set` | 해시테이블 (키만) |

```python
# 1주차 목요일에 봤던 그 차이
allowed = [1, 2, 3, ...]     # 리스트: x in allowed -> O(n)
allowed = {1, 2, 3, ...}     # 세트:   x in allowed -> O(1)
```

**드디어 그 이유가 설명됩니다.**
리스트는 하나씩 비교하고, 세트는 위치를 계산해서 바로 갑니다.

Python 3.7부터 `dict`는 **삽입 순서를 유지**합니다.
다만 이건 별도의 배열을 하나 더 둬서 구현한 것이지,
해시테이블 자체가 순서를 갖는 게 아닙니다. 정렬은 여전히 안 됩니다.

## 주니어가 자주 빠지는 함정

### 함정 1 — 가변 객체를 키로 쓰려 한다

```python
# 흔한 실수 - TypeError: unhashable type: 'list'
cache = {}
cache[[1, 2, 3]] = "result"

# 권장 - 튜플로 바꾼다
cache[(1, 2, 3)] = "result"
```

**왜 리스트는 키가 될 수 없는가.**

키를 넣을 때의 해시값으로 자리가 정해집니다.
그런데 나중에 리스트 내용이 바뀌면 해시값도 바뀝니다.
그럼 그 항목은 **엉뚱한 자리에 있는 채로 영원히 못 찾게 됩니다.**

그래서 해시테이블의 키는 **불변(immutable)이어야 합니다.**
문자열, 숫자, 튜플은 되고, 리스트, 딕셔너리, 세트는 안 됩니다.

같은 이유로 이런 실수도 위험합니다.

```python
# 위험 - 객체를 키로 쓰는데 나중에 그 필드를 바꾸면
class Device:
    def __init__(self, id):
        self.id = id
    def __hash__(self):
        return hash(self.id)

d = Device(1)
registry = {d: "sensor"}
d.id = 2                  # 해시값이 바뀜
print(d in registry)      # False. 방금 넣었는데 못 찾는다
```

### 함정 2 — `__eq__`만 정의하고 `__hash__`를 빠뜨린다

```python
# 흔한 실수
class Device:
    def __init__(self, id):
        self.id = id

    def __eq__(self, other):
        return self.id == other.id
    # __hash__를 정의하지 않으면 파이썬이 자동으로 None으로 만든다

devices = {Device(1)}     # TypeError: unhashable type

# 권장 - 둘을 함께 정의한다
class Device:
    def __init__(self, id):
        self.id = id

    def __eq__(self, other):
        return isinstance(other, Device) and self.id == other.id

    def __hash__(self):
        return hash(self.id)
```

**규칙: 같다고 판단되는 두 객체는 해시값도 같아야 합니다.**

이유는 조회 절차를 보면 명확합니다.

```
1. 해시값으로 자리를 찾는다
2. 그 자리에 있는 것과 == 로 비교한다
```

해시값이 다르면 1번에서 이미 다른 자리로 가버려서, 2번을 시도조차 안 합니다.
`__eq__`가 True를 돌려줄 기회가 없습니다.

`dataclass`를 쓰면 이걸 자동으로 처리해 줍니다.

```python
from dataclasses import dataclass

@dataclass(frozen=True)      # frozen=True면 __hash__가 자동 생성된다
class Device:
    id: int
```

### 함정 3 — 순서나 범위를 기대한다

```python
# 흔한 실수 - dict는 정렬되어 있지 않다
scores = {"c": 3, "a": 1, "b": 2}
for k in scores:
    print(k)      # 삽입 순서(c, a, b)이지 정렬 순서(a, b, c)가 아니다

# 범위 조회는 아예 불가능하다
# "키가 'a'와 'm' 사이인 것" -> 해시테이블로는 못 함
```

해시 함수가 값을 **뒤섞기 때문**입니다.
`"a"`와 `"b"`가 전혀 다른 자리에 있어서, 사이에 뭐가 있는지 알 방법이 없습니다.

**여기서 2주차 수요일 내용이 다시 이해됩니다.**

| | Hash 인덱스 | B-tree 인덱스 |
|---|---|---|
| 정확히 일치 (`=`) | O(1), 더 빠름 | O(log n) |
| 범위 (`>`, `<`, `BETWEEN`) | 불가능 | 가능 |
| 정렬 (`ORDER BY`) | 불가능 | 가능 |

DB 인덱스의 기본이 Hash가 아니라 B-tree인 이유입니다.
`=` 조회만 놓고 보면 Hash가 빠른데, 범위와 정렬을 포기할 수 없기 때문입니다.

### 함정 4 — 딕셔너리를 순회하면서 수정한다

```python
# 흔한 실수 - RuntimeError: dictionary changed size during iteration
for key in cache:
    if is_expired(cache[key]):
        del cache[key]

# 권장 - 키 목록을 먼저 확정한다
for key in list(cache.keys()):
    if is_expired(cache[key]):
        del cache[key]

# 또는 새로 만든다
cache = {k: v for k, v in cache.items() if not is_expired(v)}
```

크기가 바뀌면 리사이징이 일어나 **내부 배치가 통째로 달라집니다.**
순회 중이던 위치가 무의미해지므로 파이썬이 아예 막습니다.

2주차 목요일의 "리스트 순회 중 삭제"와 같은 부류인데,
리스트는 조용히 원소를 건너뛰고 딕셔너리는 에러를 냅니다.
**에러를 내주는 쪽이 오히려 다행입니다.**

## 트레이드오프

```
해시테이블을 쓰면
  얻는 것: 평균 O(1) 조회/삽입/삭제, 구현이 단순, 키 타입이 자유로움
  잃는 것: 순서와 범위 조회 불가, 최악의 경우 O(n),
           빈 칸을 남겨둬야 해서 메모리를 더 씀(적재율 제한),
           리사이징 순간의 지연
  손해인 상황: 범위 조회가 필요할 때, 정렬된 순회가 필요할 때,
              최악 지연이 보장되어야 하는 실시간 시스템
```

정리하면 선택 기준은 하나입니다.

> **"이거 하나" 를 찾는가, 아니면 "이 범위" 를 찾는가.**

| 필요한 것 | 자료구조 |
|---|---|
| 정확히 일치하는 하나 | 해시테이블 (dict, set, Redis) |
| 범위, 정렬, 최소/최대 | 트리 (B-tree, 정렬된 배열) |

한 가지 더. **`O(1)`이라는 표기가 "항상 빠르다"를 뜻하지는 않습니다.**

해시 함수를 계산하는 비용이 있습니다.
긴 문자열을 키로 쓰면 그 계산만으로도 시간이 걸립니다.
항목이 10개뿐이라면 리스트를 그냥 훑는 게 더 빠를 수 있습니다.

1주차 목요일 함정 4와 같은 이야기입니다.
**복잡도는 n이 충분히 클 때의 모양이지, 절대 속도가 아닙니다.**

## 연결되는 CS 지식

- **시간복잡도와 Big-O** — 1주차 목요일. 리스트 `in`이 `O(n)`이고 세트 `in`이 `O(1)`인 이유가 오늘 설명됩니다.
- **배열과 연결리스트** — 2주차 목요일. 해시테이블은 배열 위에 얹혀 있고, 체이닝에 연결리스트를 씁니다. 두 구조가 함께 쓰이는 대표 사례입니다.
- **인덱스와 B-tree** — 2주차 수요일. Hash 인덱스와 B-tree 인덱스의 갈림길이 오늘 내용입니다. 왜 DB 기본이 B-tree인지가 답해집니다.
- **캐시와 Redis** — Redis의 핵심 자료구조가 해시테이블입니다. "키로 값 하나 꺼내기"에 특화된 저장소인 이유입니다.
- **가상 메모리와 TLB** — 3주차 월요일. TLB도 일종의 캐시 조회 구조이고, 페이지 테이블도 주소를 인덱스로 바꿔 찾습니다. 같은 발상입니다.
- **정규화와 조인** — 3주차 수요일. DB의 Hash Join이 작은 테이블로 해시테이블을 만들어 큰 테이블을 훑는 방식입니다. `EXPLAIN`에서 본 그 `Hash Join`입니다.

## 다음 행동

```python
import timeit

setup = "n = 100000; lst = list(range(n)); st = set(range(n))"

print(timeit.timeit("n - 1 in lst", setup=setup, number=1000))
print(timeit.timeit("n - 1 in st",  setup=setup, number=1000))
```

n을 10배씩 늘려가며 돌려보면
리스트 쪽은 시간이 비례해서 늘고 세트 쪽은 거의 그대로입니다.

`O(n)`과 `O(1)`의 차이를 눈으로 보는 가장 짧은 실험이고,
1주차 목요일에 "set으로 바꾸면 한 글자 수정으로 복잡도가 내려간다"고 했던
그 주장의 근거이기도 합니다.
