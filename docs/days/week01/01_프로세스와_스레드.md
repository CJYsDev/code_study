# 프로세스와 스레드 — 무엇이 다른가

1일 1CS / 1주차 월요일 / 운영체제
티어: C (7섹션 전부)

---

## 한 줄 요약

프로세스와 스레드는 "일을 동시에 몇 개나 돌릴 것인가"를 정할 때,
**격리를 살 것인지 속도를 살 것인지** 고르는 두 가지 단위입니다.

---

## 이게 없으면 생기는 문제

프로세스도 스레드도 하나뿐인 서버를 상상해 봅시다.

DICONAI 같은 플랫폼에서 센서 데이터 조회 API에 요청이 들어왔고,
그 요청이 DB에서 3초짜리 집계 쿼리를 돌리고 있습니다.
이 3초 동안 서버는 **아무 일도 못 합니다.**

- 다른 사용자의 로그인 요청도 3초 뒤에 처리됩니다.
- 헬스체크 응답도 못 보내서 로드밸런서가 서버를 죽은 것으로 판단합니다.
- 센서에서 올라오는 데이터 수집 요청도 줄줄이 밀립니다.

CPU는 대부분의 시간을 **놀고 있습니다.** DB가 대답해 주기를 기다릴 뿐입니다.
놀고 있는 CPU를 쓰려면 "지금 멈춰 있는 일 말고 다른 일"을 붙여야 하고,
그 "다른 일"을 담는 그릇이 프로세스와 스레드입니다.

여기서 하나 더. 일을 여러 개 돌리기로 했다면 다음 질문이 따라옵니다.

> 이 일들이 서로의 데이터를 봐도 되는가?

- 봐도 안 되면 → 프로세스 (메모리를 따로 준다)
- 봐야 편하면 → 스레드 (메모리를 같이 쓴다)

이 한 줄이 둘의 차이 전부입니다.

---

## 비유

**프로세스는 별도의 주방이고, 스레드는 같은 주방의 요리사입니다.**

주방을 하나 더 짓는 것(프로세스)은 비쌉니다. 냉장고, 가스레인지, 재료를 전부 새로 갖춰야 합니다.
대신 A주방에서 불이 나도 B주방은 멀쩡합니다.

같은 주방에 요리사를 한 명 더 넣는 것(스레드)은 쌉니다. 사람만 들어오면 됩니다.
대신 **같은 냉장고를 씁니다.** 한 명이 마지막 계란을 가져갔는데
다른 한 명이 그걸 모르고 계란을 쓰려 하면 사고가 납니다. 이게 race condition입니다.

단, 이 비유가 맞지 않는 부분: 실제 주방은 요리사를 늘리면 그만큼 빨라지지만,
CPU는 코어 수를 넘어서면 더 늘려도 빨라지지 않습니다.
Python에서는 GIL 때문에 그 한계가 훨씬 일찍 옵니다. (아래에서 다룹니다)

---

## 실제로 어떻게 동작하는가

### 둘의 비교

| 항목 | 프로세스 | 스레드 |
|---|---|---|
| 메모리 공간 | 각자 독립 (코드/데이터/힙 전부 따로) | 코드·데이터·힙 공유, 스택만 각자 |
| 생성 비용 | 비쌈 (메모리 공간을 새로 할당) | 쌈 (스택과 레지스터만) |
| 통신 방법 | IPC 필요 (소켓, 파이프, 공유메모리) | 그냥 변수 공유 |
| 하나가 죽으면 | 나머지는 멀쩡 | 프로세스 전체가 같이 죽을 수 있음 |
| 컨텍스트 스위칭 | 비쌈 (메모리 매핑 정보까지 교체) | 쌈 (메모리 매핑은 그대로) |

핵심은 **"메모리를 공유하는가"** 한 줄이고, 나머지 항목은 전부 여기서 파생됩니다.
메모리를 따로 쓰니까 생성이 비싸고, 통신이 번거롭고, 대신 서로 안 죽입니다.

### Python의 GIL

Python(CPython)에는 GIL(Global Interpreter Lock)이 있습니다.
**한 프로세스 안에서는 아무리 스레드가 많아도 Python 바이트코드를 실행하는 스레드는 항상 1개**입니다.

그래서 이런 결과가 나옵니다.

| 작업 성격 | 스레드를 늘리면 | 이유 |
|---|---|---|
| IO-bound (DB 조회, 외부 API 호출, 파일 읽기) | 빨라짐 | IO를 기다리는 동안 GIL을 놓아줌 |
| CPU-bound (이미지 처리, 대량 연산, 암호화) | 안 빨라짐 | GIL을 계속 붙잡고 있음 |

CPU-bound 작업을 병렬로 돌리려면 스레드가 아니라 **프로세스**를 늘려야 합니다.
GIL은 프로세스마다 하나씩 있기 때문입니다.

참고로 Python 3.13부터 GIL을 끄는 free-threaded 빌드가 실험적으로 제공되지만,
아직 기본값이 아니고 생태계 지원도 완전하지 않습니다.
당분간은 위 표대로 판단하면 됩니다.

### 웹 서버에 대입하면

**Django + gunicorn**

```bash
gunicorn config.wsgi --workers 4 --threads 2
```

- `--workers 4` → 프로세스 4개. 각각이 Django 앱 전체를 메모리에 통째로 올림
- `--threads 2` → 각 프로세스 안에 스레드 2개
- 동시에 붙잡을 수 있는 요청: 4 × 2 = 8개

**FastAPI + uvicorn**

```bash
uvicorn main:app --workers 4
```

FastAPI는 여기에 축이 하나 더 있습니다. 각 프로세스 안에서 **이벤트 루프**가 돕니다.

- `async def` 엔드포인트 → 이벤트 루프가 처리. 스레드를 안 늘려도 IO 대기 중 다른 요청을 받음
- `def` (동기) 엔드포인트 → 스레드풀로 넘겨서 처리

즉 동시성을 만드는 방법이 프로세스 / 스레드 / 이벤트 루프 세 가지인 셈입니다.
이벤트 루프는 4주차 "동기/비동기, 블로킹/논블로킹"에서 이어서 봅니다.

## 주니어가 자주 빠지는 함정

### 함정 1 — 전역변수로 상태를 공유하려 한다

worker가 여러 개면 각 프로세스가 **자기만의 사본**을 가집니다. 절대 공유되지 않습니다.

```python
# 흔한 실수 - worker 4개면 카운터가 4개로 쪼개진다
request_count = 0

@app.get("/ping")
def ping():
    global request_count
    request_count += 1
    return {"count": request_count}   # 요청마다 값이 들쭉날쭉

# 권장 - 프로세스 밖의 공용 저장소를 쓴다
import redis
r = redis.Redis()

@app.get("/ping")
def ping():
    return {"count": r.incr("request_count")}
```

로컬에서 `runserver`(단일 프로세스)로 테스트하면 멀쩡히 동작합니다.
배포 후에야 터지기 때문에 원인을 찾기 어려운 유형입니다.
인메모리 캐시, 로그인 세션, 스케줄러 등록도 전부 같은 함정입니다.

### 함정 2 — CPU 작업에 스레드를 늘린다

```python
# 흔한 실수 - GIL 때문에 스레드를 늘려도 안 빨라진다
from concurrent.futures import ThreadPoolExecutor

def analyze(data):
    return heavy_calculation(data)   # 순수 Python 연산

with ThreadPoolExecutor(max_workers=8) as ex:
    results = list(ex.map(analyze, sensor_batches))

# 권장 - CPU-bound는 프로세스로
from concurrent.futures import ProcessPoolExecutor

with ProcessPoolExecutor(max_workers=4) as ex:
    results = list(ex.map(analyze, sensor_batches))
```

다만 프로세스는 데이터를 직렬화해서 주고받기 때문에,
작업 하나가 짧으면 오히려 느려집니다. 작업 단위가 충분히 클 때만 이득입니다.

### 함정 3 — worker 수를 무작정 늘린다

worker 하나가 Django/FastAPI 앱 전체를 메모리에 올립니다.
앱이 300MB를 먹는다면 worker 8개는 약 2.4GB입니다. OOM으로 컨테이너가 죽습니다.

```python
# 흔한 실수 - 근거 없이 큰 수
workers = 16

# 권장 - 코어 수 기준에서 출발해 실측으로 조정
import multiprocessing
workers = multiprocessing.cpu_count() * 2 + 1
```

`cpu_count() * 2 + 1`은 gunicorn 문서의 출발점 권장값이지 정답이 아닙니다.
IO 대기가 길면 더 늘려도 되고, 메모리가 빠듯하면 줄여야 합니다.
**2주차 금요일 통합 과제**가 정확히 이 값을 실측으로 정하는 작업입니다.

### 함정 4 — 스레드 여러 개가 같은 데이터를 건드린다

```python
# 흔한 실수 - 읽고 쓰는 사이에 다른 스레드가 끼어들 수 있다
balance = 100

def withdraw(amount):
    global balance
    if balance >= amount:      # 여기서 통과했는데
        balance -= amount      # 여기 오기 전에 다른 스레드가 이미 뺐다면?

# 권장 - 임계 구역을 락으로 감싼다
import threading
lock = threading.Lock()

def withdraw(amount):
    global balance
    with lock:
        if balance >= amount:
            balance -= amount
```

"GIL이 있으니 Python은 스레드 안전하다"는 오해가 흔한데, 사실이 아닙니다.
GIL은 바이트코드 **한 줄** 단위로 보호할 뿐이고, 위처럼 여러 줄에 걸친 로직은 중간에 끊깁니다.

## 트레이드오프

```
프로세스를 늘릴 때
  얻는 것: 진짜 병렬 실행(GIL 우회), 장애 격리, 하나 죽어도 나머지 생존
  잃는 것: 메모리 사용량이 배수로 증가, 프로세스 간 통신 비용, 상태 공유 불가
  안 맞는 때: 메모리가 빠듯한 환경, 작업 단위가 아주 짧은 경우

스레드를 늘릴 때
  얻는 것: 낮은 생성 비용, 빠른 컨텍스트 스위칭, 변수 그대로 공유
  잃는 것: race condition 위험, 디버깅 난이도 급상승, 하나가 죽으면 전체 위험
  안 맞는 때: CPU-bound 작업 (GIL), 공유 상태가 복잡한 로직
```

실무에서는 보통 **둘을 섞습니다.**
프로세스는 코어 수 기준으로 몇 개, 그 안에서 IO 대기를 메우려고 스레드를 조금.
어느 쪽을 늘릴지 판단하는 기준은 결국 **"이 서비스가 CPU를 쓰느라 바쁜가, 기다리느라 바쁜가"** 한 가지입니다.

## 연결되는 CS 지식

- **컨텍스트 스위칭과 스케줄링** — 프로세스 전환이 왜 스레드 전환보다 비싼지, 그 비용의 정체가 무엇인지 알게 됩니다. (2주차 월요일 주제)
- **가상 메모리와 페이징** — "프로세스마다 독립된 메모리 공간"이 물리적으로 어떻게 가능한지 설명해 줍니다. (3주차 월요일 주제)
- **임계 구역과 상호 배제** — 락이 필요한 이유와, 락을 잘못 걸면 왜 데드락이 생기는지로 이어집니다.
- **동기/비동기, 블로킹/논블로킹** — 스레드를 늘리지 않고도 동시성을 얻는 세 번째 길입니다. (4주차 월요일 주제)
