## 한 줄 요약

가상 메모리는 **모든 프로세스에게 "이 메모리 전부 네 것"이라고 거짓말하는 장치**입니다.
1주차에 본 "프로세스마다 독립된 주소 공간"이 물리적으로 어떻게 가능한지가 여기서 설명됩니다.

## 이게 없으면 생기는 문제

### 문제 1 — 프로그램이 서로의 메모리를 밟는다

프로그램이 물리 메모리 주소를 직접 쓴다고 해봅시다.

Django 서버가 주소 1000번에 세션 정보를 씁니다.
동시에 돌던 다른 프로그램이 같은 1000번에 자기 데이터를 씁니다.
Django의 세션이 소리 없이 뭉개집니다.

막을 방법이 없습니다. **주소가 곧 실제 위치**라서, 누구나 아무 데나 쓸 수 있습니다.
프로그램 하나의 버그가 시스템 전체를 무너뜨립니다.

1주차에 "프로세스는 메모리가 독립되어 있어서 하나가 죽어도 나머지는 멀쩡하다"고 배웠는데,
그 격리를 실제로 만들어주는 게 오늘 주제입니다.

### 문제 2 — 컴파일 시점에 주소를 못 정한다

프로그램을 만들 때 "내 데이터는 1000번지에 둔다"고 정해두면,
그 자리에 다른 프로그램이 이미 있을 때 실행이 안 됩니다.
실행할 때마다 빈 자리를 찾아 주소를 전부 다시 계산해야 합니다.

### 문제 3 — 물리 메모리보다 큰 프로그램을 못 돌린다

메모리가 8GB인데 프로그램이 10GB를 쓰려 하면 실행 자체가 불가능합니다.

실제로는 프로그램이 **자기 코드 전부를 동시에 쓰지 않습니다.**
예외 처리 코드, 관리자 기능, 초기화 로직은 대부분 시간 동안 잠들어 있습니다.
지금 쓰는 부분만 메모리에 올려두면 되는데, 그 구분이 불가능합니다.

가상 메모리는 이 세 가지를 한 번에 해결합니다.

## 비유

**아파트 호수와 실제 위치입니다.**

모든 동에 "101호"가 있습니다. 101동 101호, 102동 101호.
주민들은 전부 "우리 집은 101호"라고 말하지만 실제 위치는 전부 다릅니다.
같은 번호를 써도 충돌하지 않습니다. **동 번호가 있기 때문**입니다.

프로세스마다 "0번지부터 시작하는 자기만의 주소 체계"를 갖는 것이 이겁니다.
`0x400000`이라는 주소를 모든 프로세스가 쓰지만, 실제로 가리키는 물리 위치는 전부 다릅니다.
그 변환을 해주는 게 **페이지 테이블**이고, 관리인이 **MMU**입니다.

단, 이 비유가 놓치는 부분: 아파트는 집이 항상 그 자리에 있지만,
가상 메모리는 **당장 안 쓰는 집을 창고(디스크)로 옮겨둡니다.**
찾아갔는데 비어 있을 수 있고, 그때 창고에서 도로 꺼내옵니다.
이게 페이지 폴트입니다.

---

## 실제로 어떻게 동작하는가

### 주소 변환

```
프로세스가 쓰는 주소          변환                실제 위치
   가상 주소       -->   [MMU + 페이지 테이블]   -->   물리 주소
   0x400000                                          0x1A2B000
```

메모리를 바이트 단위로 관리하면 변환 표가 너무 커집니다.
그래서 **고정 크기 덩어리**로 잘라서 관리합니다. 보통 4KB.

- 가상 메모리 쪽 덩어리 = **페이지(page)**
- 물리 메모리 쪽 덩어리 = **프레임(frame)**

페이지 테이블은 "이 페이지는 저 프레임에 있다"는 대응표입니다.
프로세스마다 하나씩 갖습니다. 그래서 같은 가상 주소가 다른 물리 위치를 가리킵니다.

### TLB — 2주차 월요일에 나왔던 그것

주소 변환을 매번 페이지 테이블을 뒤져서 하면, 메모리 접근 한 번에 접근이 두 번 필요합니다.
그래서 **최근 변환 결과를 캐시**해둡니다. 이게 TLB(Translation Lookaside Buffer)입니다.

```
TLB 적중 -> 변환이 사실상 공짜
TLB 미스 -> 페이지 테이블을 실제로 조회 (수십~수백 배 느림)
```

여기서 2주차 월요일 내용이 완성됩니다.

**프로세스를 전환하면 주소 체계 자체가 바뀝니다.**
102동 주소표를 들고 101동을 찾아가면 안 되니까, TLB를 통째로 비웁니다.
비워진 TLB가 다시 채워질 때까지 모든 메모리 접근이 느립니다.

스레드 전환은 같은 프로세스 안이라 주소 체계가 그대로입니다. TLB를 비울 필요가 없습니다.
**"프로세스 전환이 스레드 전환보다 비싸다"의 정확한 이유가 이것입니다.**

### 페이지 폴트

접근하려는 페이지가 물리 메모리에 없을 때 발생합니다.

```
1. 프로세스가 어떤 주소에 접근
2. 페이지 테이블 확인 -> 물리 메모리에 없음
3. 페이지 폴트 발생, 커널이 개입
4. 디스크에서 해당 페이지를 읽어와 빈 프레임에 올림
5. 페이지 테이블 갱신
6. 실패했던 명령을 다시 실행
```

4번이 디스크 접근이라 **밀리초 단위**입니다. 메모리 접근의 수만 배입니다.

폴트에는 종류가 있습니다.

| 종류 | 상황 | 비용 |
|---|---|---|
| Minor fault | 이미 메모리에 있는데 매핑만 안 된 경우 | 쌈 |
| Major fault | 디스크에서 실제로 읽어와야 하는 경우 | 비쌈 |

`ps -o min_flt,maj_flt -p <PID>`로 확인할 수 있습니다.
major fault가 계속 늘어나면 **메모리가 부족하다는 신호**입니다.

### 요구 페이징과 스와핑

프로그램을 실행할 때 전부 메모리에 올리지 않습니다.
**접근할 때 그때 올립니다.** 이게 요구 페이징(demand paging)입니다.

덕분에 시작이 빠르고, 안 쓰는 부분은 아예 안 올라갑니다.
물리 메모리보다 큰 프로그램도 돌아가는 이유입니다.

메모리가 부족하면 안 쓰는 페이지를 디스크로 내보냅니다(스왑 아웃).
다시 필요해지면 도로 가져옵니다(스왑 인).

### 스래싱

스왑이 과해지면 이런 상태가 됩니다.

```
A 페이지를 올리려고 B를 내보냄
-> B가 필요해져서 다시 올리려고 C를 내보냄
-> C가 필요해져서...
```

CPU는 놀고 디스크만 돌아갑니다. 시스템 전체가 정지한 것처럼 느껴집니다.
2주차 월요일에 본 컨텍스트 스위칭 스래싱과 이름은 같지만 **원인이 다릅니다.**
그쪽은 CPU 경쟁, 이쪽은 메모리 부족입니다.

### Copy-on-Write

프로세스를 만들 때 부모 메모리를 전부 복사하면 매우 비쌉니다.
그래서 처음엔 **같은 물리 페이지를 함께 가리키게** 해둡니다.
누군가 쓰기를 시도할 때 그 페이지만 복사합니다.

```
fork() 직후 : 부모와 자식이 같은 프레임을 공유 (읽기 전용 표시)
쓰기 발생   : 그 페이지만 복사해서 각자 갖기
```

1주차에 "프로세스 생성이 비싸다"고 했지만, CoW 덕분에 생각만큼은 아닙니다.
gunicorn이 worker를 fork로 만들 때 메모리가 정확히 배수로 늘지 않는 이유가 이것입니다.

## 주니어가 자주 빠지는 함정

### 함정 1 — 컨테이너 메모리 제한을 프로세스가 모른다고 생각하지 않는다

```python
# 흔한 실수 - 호스트 전체 메모리를 기준으로 판단
import psutil
total = psutil.virtual_memory().total       # 컨테이너 제한이 아니라 호스트 값

# 권장 - cgroup 제한을 직접 읽는다
def container_memory_limit():
    try:
        with open("/sys/fs/cgroup/memory.max") as f:   # cgroup v2
            value = f.read().strip()
            return None if value == "max" else int(value)
    except FileNotFoundError:
        return None
```

컨테이너에 512MB 제한을 걸어도, 안에서 보면 호스트의 전체 메모리가 보입니다.
"메모리 넉넉하네"라고 판단하고 worker를 늘리면 OOM Killer에게 죽습니다.

그리고 컨테이너에서 죽을 때는 보통 **파이썬 예외가 아니라 프로세스가 통째로 사라집니다.**
로그에 아무것도 안 남아서 원인 찾기가 어렵습니다. `dmesg`나 `kubectl describe pod`를 봐야 합니다.

### 함정 2 — worker 메모리를 단순 곱셈으로 계산한다

```
앱 하나가 300MB -> worker 8개면 2.4GB?
```

CoW 때문에 실제로는 이보다 적습니다. 코드 영역은 공유되기 때문입니다.
그런데 **파이썬에서는 이 이득이 생각보다 빨리 사라집니다.**

파이썬 객체마다 참조 카운트가 있고, 읽기만 해도 그 값이 바뀝니다.
쓰기가 일어난 것으로 간주되어 페이지가 복사됩니다.

```python
# 참고 - 공유 이득을 늘리려면 fork 전에 미리 로드해둔다
# gunicorn
#   --preload   앱을 마스터에서 먼저 로드한 뒤 fork
```

`--preload`는 메모리를 아끼지만, 코드 변경 시 전체 재시작이 필요해집니다.
무중단 배포 방식과 충돌할 수 있으니 확인하고 쓰는 게 좋습니다.

### 함정 3 — 큰 파일을 통째로 읽는다

```python
# 흔한 실수 - 2GB 파일이면 2GB를 메모리에 올린다
with open("sensor_dump.csv") as f:
    content = f.read()
    for line in content.split("\n"):
        process(line)

# 권장 - 한 줄씩 흘려보낸다
with open("sensor_dump.csv") as f:
    for line in f:
        process(line)
```

QuerySet도 같습니다.

```python
# 흔한 실수 - 전체를 파이썬 객체로 만들어 메모리에 올림
for m in Measurement.objects.all():
    process(m)

# 권장 - 일정 크기씩 나눠서 가져온다
for m in Measurement.objects.all().iterator(chunk_size=2000):
    process(m)
```

메모리가 부족해지면 스왑이 시작되고, 스왑이 시작되면 **디스크 속도로 떨어집니다.**
"조금 느려지는" 게 아니라 수천 배 느려집니다.

### 함정 4 — 메모리 사용량 지표를 잘못 읽는다

`top`이나 `ps`에서 보이는 값이 여러 개인데 의미가 다릅니다.

| 지표 | 의미 |
|---|---|
| VSZ / VIRT | 가상 주소 공간 크기. 실제로 안 쓰는 것도 포함 |
| RSS / RES | 실제 물리 메모리 점유량 |
| SHR | 다른 프로세스와 공유 중인 부분 |

VSZ가 크다고 놀랄 필요 없습니다. 주소 공간을 예약만 해둔 것도 포함됩니다.
**실제로 봐야 하는 건 RSS**입니다.

worker가 여러 개일 때는 RSS를 단순 합산하면 공유분이 중복 계산됩니다.
정확히 보려면 PSS(Proportional Set Size)를 봐야 합니다.

## 트레이드오프

```
가상 메모리를 쓰면
  얻는 것: 프로세스 간 완전한 격리, 물리 메모리보다 큰 프로그램 실행,
           주소 배치를 실행 시점에 결정, CoW로 프로세스 생성 비용 절감
  잃는 것: 주소 변환 오버헤드(TLB 미스 시), 페이지 테이블 자체가 메모리를 씀,
           페이지 폴트 시 디스크 접근, 프로세스 전환 시 TLB 무효화
  손해인 상황: 실시간성이 절대적인 임베디드 시스템
              -> 예측 불가능한 페이지 폴트 지연을 허용할 수 없어서 가상 메모리를 안 쓰기도 함
```

여기서 페이지 크기의 거래도 나옵니다.

```
페이지를 크게 (2MB huge page)
  얻는 것: 페이지 테이블 항목 수 감소, TLB 적중률 상승
  잃는 것: 내부 단편화 (작은 데이터에도 큰 덩어리를 할당)

페이지를 작게 (4KB)
  얻는 것: 메모리 낭비 감소
  잃는 것: 테이블이 커지고 TLB 미스가 늘어남
```

DB처럼 큰 메모리를 다루는 프로그램은 huge page로 이득을 봅니다.

한 가지 더. **가상 메모리의 편리함이 문제를 숨깁니다.**
메모리가 부족해도 프로그램은 에러 없이 그냥 느려집니다.
"코드는 그대로인데 갑자기 느려졌다"의 원인이 스왑인 경우가 꽤 있습니다.
`vmstat`의 `si`/`so` 열(스왑 인/아웃)이 0이 아니면 이걸 의심합니다.

## 연결되는 CS 지식

- **프로세스와 스레드** — 1주차 월요일의 "독립된 메모리 공간"이 오늘 내용으로 구현됩니다.
- **컨텍스트 스위칭** — 2주차 월요일의 TLB 무효화가 왜 비싼지가 오늘 완성됩니다.
- **캐시 지역성** — 2주차 목요일의 배열이 빠른 이유와 같은 뿌리입니다. 붙어 있는 데이터는 같은 페이지에 들어가 TLB 미스도 줄입니다.
- **B-tree와 디스크 블록** — 2주차 수요일에서 본 "블록 단위로 읽는다"가 페이지와 같은 개념입니다. DB와 OS가 같은 이유로 같은 설계를 했습니다.
- **메모리 매핑 파일(mmap)** — 파일을 메모리처럼 다루는 기법. 가상 메모리를 응용한 대표 사례입니다.


보통 vsz가 rss의 몇 배로 나오는데, 그 차이가 **약속만 하고 실제로는 안 쓰는 공간**입니다.
