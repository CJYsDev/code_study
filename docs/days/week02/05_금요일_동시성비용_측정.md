# worker를 늘리면 어디까지 빨라지고 어디서부터 손해인가

1일 1CS / 2주차 금요일 / 통합 과제

이번 주 네 주제가 전부 "비싼 것에 덜 가는 법"이었다.
그 비용이 실제로 존재한다는 것을 숫자로 확인한다.

| 주제 | 이 과제에서 확인하는 것 |
|---|---|
| 컨텍스트 스위칭 (월) | 워커를 늘리면 어느 지점부터 손해인가 |
| TCP handshake (화) | 연결 재사용이 왕복 지연을 얼마나 줄이는가 |
| B-tree 인덱스 (수) | 디스크 읽기 횟수가 왜 기준인가 |
| 배열 vs 연결리스트 (목) | 캐시 지역성이 실측에서 얼마나 차이 나는가 |

코드: [`lab/week02_fri_concurrency_lab.py`](../../../lab/week02_fri_concurrency_lab.py)

> 주의 — 이 문서는 `[1]`~`[6]` 블록을 전제하지만 현재 스크립트에는 `[1]`~`[4]`만 있다.
> `[5]` 캐시 지역성과 `[6]` 연결 재사용은 아직 구현되지 않았다.

## 1단계 — 실행 주체 확인

스크립트의 첫 블록이 PID와 TID를 출력한다.

| 실행 방식 | PID | TID |
|---|---|---|
| 메인 스레드 | 1종류 | 1종류 |
| 스레드 4개 | 1종류 | 4종류 |
| 프로세스 4개 | 4종류 | 각자 다름 |

1주차 월요일의 "스레드는 메모리를 공유하고 프로세스는 안 한다"가
PID가 같은지 다른지로 드러난다.

## 2단계 — CPU 작업에 스레드를 늘린다

스크립트의 `[2]` 블록.

| 워커 수 | 총 시간(초) | 1개 기준 배속 |
|---|---|---|
| 1 | | 1.00x |
| 2 | | |
| 4 | | |
| 8 | | |
| 16 | | |

**예상: 배속이 1.0 근처에 머문다.**

GIL 때문에 한 프로세스 안에서는 파이썬 바이트코드를 실행하는 스레드가 항상 하나입니다.
스레드를 늘려도 실행할 수 있는 건 여전히 하나입니다.

워커를 아주 많이 늘리면 **1.0보다 떨어지기도 합니다.**
일은 그대로인데 전환 비용만 늘었기 때문입니다. 2주차 월요일의 컨텍스트 스위칭 비용입니다.

## 3단계 — IO 작업에 스레드를 늘린다

스크립트의 `[3]` 블록.

| 워커 수 | 총 시간(초) | 1개 기준 배속 |
|---|---|---|
| 1 | | 1.00x |
| 2 | | |
| 4 | | |
| 8 | | |
| 16 | | |

**예상: 워커 수만큼 빨라지다가 평평해진다.**

IO를 기다리는 동안에는 GIL을 놓습니다. 그래서 스레드들이 겹쳐서 진행합니다.

평평해지는 지점을 기록해 둡니다. 작업 개수에 도달하면 더 늘려도 소용이 없습니다.

| 항목 | 값 |
|---|---|
| 배속이 더 안 오르기 시작한 워커 수 | |

## 4단계 — CPU 작업에 프로세스를 늘린다

스크립트의 `[4]` 블록.

| 워커 수 | 총 시간(초) | 1개 기준 배속 |
|---|---|---|
| 1 | | 1.00x |
| 2 | | |
| 4 | | |
| 8 | | |
| 16 | | |

**예상: 코어 수까지 빨라지고 그 뒤로는 이득이 사라진다.**

프로세스마다 GIL이 따로 있으므로 진짜 병렬 실행이 됩니다.
다만 코어 수를 넘어서면 CPU가 물리적으로 부족해서 더 늘려도 소용없습니다.

`[2]`와 `[4]`를 나란히 놓고 봅니다.
**같은 CPU 작업인데 스레드는 안 빨라지고 프로세스는 빨라집니다.**
GIL이 실재한다는 가장 직접적인 증거입니다.

## 5단계 — 캐시 지역성 확인

스크립트의 `[5]` 블록. 2주차 목요일 내용이다.

| 자료구조 | 100만 개 순회 시간 |
|---|---|
| list (배열) | |
| deque (블록 연결 구조) | |

복잡도는 둘 다 `O(n)`인데 실측이 다릅니다.
배열은 값들이 메모리에 붙어 있어서, 하나를 읽으면 다음 몇 개가 이미 캐시에 와 있습니다.

이어서 `pop(0)` vs `popleft()` 비교도 나옵니다.

| 연산 | n=10,000 | n=50,000 | n=100,000 |
|---|---|---|---|
| `list.pop(0)` | | | |
| `deque.popleft()` | | | |

n을 5배로 늘렸을 때 **list는 25배, deque는 5배**로 늘어납니다.
`O(n²)`와 `O(n)`의 차이입니다.

---

## 6단계 — 연결 재사용 확인 (선택)

인터넷이 되는 환경에서만 가능하다. 2주차 화요일 내용이다.

스크립트의 `[6]` 블록에서 같은 서버에 10번 요청을 보낸다.

| 방식 | 총 시간 |
|---|---|
| 매번 새 연결 | |
| 연결 재사용 | |

첫 요청은 둘 다 비슷하고, **두 번째부터 차이가 벌어집니다.**
handshake와 TLS 협상을 건너뛰기 때문입니다.

이게 `httpx.AsyncClient`를 재사용해야 하는 이유이고,
Django의 `CONN_MAX_AGE`가 존재하는 이유입니다.

## 정리

표를 다 채웠다면 다음을 자기 말로 설명할 수 있어야 한다.

1. 왜 CPU 작업은 스레드로 안 빨라지고 프로세스로는 빨라지는가
2. 워커를 늘리는 게 손해로 뒤집히는 지점은 무엇이 결정하는가
3. 내 서비스의 worker 수를 지금 몇으로 두어야 하는가, 그 근거는 무엇인가

3번의 판단 기준:

```
CPU를 쓰느라 바쁘다  -> 코어 수 근처
기다리느라 바쁘다     -> 코어 수보다 더 늘려도 이득
```

어느 쪽인지 모르겠다면, 운영 서버에서 `top`을 띄워두고
평상시 CPU 사용률을 봅니다. 80% 이상 계속 붙어 있으면 앞쪽,
20%대에서 노는데 응답이 느리면 뒤쪽입니다.

## 실무로 옮길 것

- [ ] 현재 gunicorn/uvicorn worker 수는 몇이고 근거가 있는가
- [ ] 코어 수와 비교했을 때 적절한가 (`nproc` 또는 `os.cpu_count()`)
- [ ] worker 수 × CONN_MAX_AGE가 DB `max_connections`를 넘지 않는가
- [ ] CPU-bound 작업(이미지 처리, 대량 집계)을 스레드풀로 돌리는 곳이 있는가
- [ ] HTTP 클라이언트를 요청마다 새로 만드는 곳이 있는가

마지막 두 항목은 **지금 코드에서 바로 찾아볼 수 있는 것**입니다.
`ThreadPoolExecutor`와 `httpx.AsyncClient()` / `requests.get(`을 검색해 보면 됩니다.
