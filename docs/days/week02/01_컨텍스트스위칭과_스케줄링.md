# 컨텍스트 스위칭과 스케줄링 — 무엇에 대한 비용인가

1일 1CS / 2주차 월요일 / 운영체제
티어: C (7섹션 전부)

---

## 한 줄 요약

컨텍스트 스위칭은 **CPU가 일을 바꿔 잡을 때 치르는 비용**이고,
스케줄링은 **다음에 누구를 잡을지 정하는 규칙**입니다.
지난주에 배운 "동시성"이 왜 공짜가 아닌지가 여기서 설명됩니다.

---

## 이게 없으면 생기는 문제

### 문제 1 — "늘리면 빨라진다"가 어디까지 참인지 모른다

1주차 월요일에 프로세스와 스레드를 늘리면 동시에 일할 수 있다고 배웠습니다.
그럼 자연스럽게 이런 질문이 남습니다.

> 그럼 worker를 64개로 늘리면 16배 빨라지나?

안 그렇습니다. 오히려 느려지는 구간이 옵니다.

CPU 코어가 4개인데 실행 대기 중인 스레드가 100개라면,
CPU는 100개를 동시에 돌리는 게 아니라 **아주 빠르게 번갈아 가며** 조금씩 실행합니다.
그 "번갈아"가 공짜라면 문제가 없겠지만, 매번 값을 치릅니다.

어느 지점을 넘어서면 CPU가 **실제 일보다 일을 바꾸는 데 더 많은 시간**을 씁니다.
이 상태를 thrashing이라고 부릅니다.
"worker를 늘렸는데 응답이 더 느려졌다"는 현상의 정체입니다.

이 비용의 존재를 모르면 성능 튜닝이 그냥 숫자 찍어보기가 됩니다.
알면 "어느 방향으로 왜 움직여야 하는지"를 설명할 수 있습니다.

### 문제 2 — 하나가 CPU를 놓지 않으면 전부 멈춘다

스케줄러가 강제로 개입하지 않는다면, 무한 루프에 빠진 프로그램 하나가
시스템 전체를 정지시킵니다. 마우스도 안 움직입니다.

실제로 초기 운영체제(Windows 3.x, 초기 Mac OS)가 이랬습니다.
프로그램이 자발적으로 CPU를 반납해야만 다른 프로그램이 실행됐습니다.
지금은 커널이 타이머 인터럽트로 강제 회수합니다. 이걸 **선점(preemption)**이라고 합니다.

## 비유

**요리사 한 명이 주문 여러 개를 번갈아 처리하는 상황입니다.**

주문 A를 하다가 B로 넘어가려면, 도마를 치우고 A의 재료를 넣어두고
B의 재료를 꺼내고 레시피를 다시 확인해야 합니다.
이 **준비 시간이 컨텍스트 스위칭**입니다.

주문이 5개일 때는 문제가 없습니다.
주문 50개를 1분씩 돌아가며 처리하면, 하루 종일 재료만 꺼냈다 넣었다 하다 끝납니다.
어느 주문도 완성되지 않습니다.

그리고 "다음에 어느 주문을 잡을까"를 정하는 규칙이 **스케줄링**입니다.
먼저 들어온 순서대로 할지, 빨리 끝나는 것부터 할지, VIP를 먼저 할지.

단, 이 비유가 놓치는 부분: 요리사는 머릿속 기억으로 이어가지만
CPU는 전환할 때 **캐시에 쌓아둔 데이터가 통째로 무의미해집니다.**
실제 비용의 대부분이 여기서 나옵니다. 아래에서 이어집니다.

---

## 실제로 어떻게 동작하는가

### 컨텍스트란 무엇인가

"하던 일을 나중에 정확히 이어서 하기 위해 저장해야 하는 상태 전부"입니다.

| 저장 대상 | 무엇인가 |
|---|---|
| 프로그램 카운터 | 다음에 실행할 명령어 위치 |
| 레지스터 | 계산 중이던 값들 |
| 스택 포인터 | 현재 함수 호출 위치 |
| 메모리 매핑 정보 | 이 프로세스의 주소 공간 (프로세스 전환 시에만) |

이 묶음을 커널이 PCB(Process Control Block)에 보관합니다.

### 전환 절차

```
1. 현재 실행 중인 것의 상태를 PCB에 저장
2. 스케줄러가 다음에 실행할 것을 선택
3. 그것의 PCB에서 상태를 복원
4. 실행 재개
```

### 비용은 두 종류입니다

**직접 비용** — 위 1~3번. 레지스터를 저장하고 복원하는 시간. 보통 수 마이크로초.

**간접 비용** — 이쪽이 훨씬 큽니다.

CPU에는 캐시(L1/L2/L3)가 있습니다. 자주 쓰는 데이터를 가까이 두는 창고입니다.
그런데 다른 작업으로 전환하면, 그 작업은 **전혀 다른 데이터**를 씁니다.
캐시에 있던 것이 전부 쓸모없어지고, 다시 메모리에서 끌어와야 합니다.

메모리 접근은 캐시 접근보다 수십 배에서 백 배 느립니다.
전환 직후 한동안 이 느린 상태로 동작합니다. 이게 진짜 비용입니다.

### 프로세스 전환이 스레드 전환보다 비싼 이유

| | 스레드 전환 (같은 프로세스 내) | 프로세스 전환 |
|---|---|---|
| 레지스터 교체 | 필요 | 필요 |
| 메모리 주소 공간 교체 | 불필요 (공유) | 필요 |
| TLB 무효화 | 없음 | 발생 |

TLB는 가상 주소를 물리 주소로 바꾸는 결과를 저장해둔 캐시입니다.
프로세스가 바뀌면 주소 체계 자체가 달라지므로 이걸 비워야 합니다.
비워진 TLB가 다시 채워질 때까지 메모리 접근이 느려집니다.

1주차에 "스레드가 프로세스보다 가볍다"고 한 이유의 절반이 이겁니다.
왜 주소 공간이 프로세스마다 다른지는 3주차 월요일 "가상 메모리와 페이징"에서 이어집니다.

### 전환은 언제 일어나는가

- **타임 슬라이스 만료** — 정해진 시간을 다 썼을 때 (선점)
- **IO 대기 시작** — DB 응답이나 파일 읽기를 기다릴 때. **자발적으로 CPU를 놓습니다**
- **더 우선순위 높은 작업 도착**
- **인터럽트 발생** — 네트워크 패킷 도착, 키보드 입력 등

두 번째가 중요합니다. IO를 기다리는 동안 CPU를 놓기 때문에,
IO-bound 작업은 스레드를 코어 수보다 많이 띄워도 이득이 납니다.
1주차에 본 "IO-bound면 스레드, CPU-bound면 프로세스"의 근거가 이것입니다.

### 프로세스의 상태

```
new --> ready <---------> running --> terminated
          ^                  |
          |                  v
          +----------- waiting
                   (IO 완료를 기다림)
```

`running`에 들어갈 수 있는 개수가 **코어 수**입니다.
나머지는 전부 `ready`에서 줄을 섭니다.
`ready` 줄이 길어질수록 각자의 차례가 늦게 오고, 응답 시간이 늘어납니다.

### 스케줄링 알고리즘

| 방식 | 규칙 | 문제점 |
|---|---|---|
| FCFS | 먼저 온 순서대로 | 앞의 긴 작업이 뒤를 전부 막음 (convoy effect) |
| SJF | 짧은 것부터 | 실행 시간을 미리 알 수 없음, 긴 작업이 영원히 밀림 |
| Round Robin | 일정 시간씩 돌아가며 | 공평하지만 전환 횟수가 많아짐 |
| Priority | 우선순위 높은 것부터 | 낮은 것이 계속 밀림 (starvation) |
| MLFQ | 여러 큐를 두고 동적으로 우선순위 조정 | 복잡함 |

리눅스는 현재 CFS(Completely Fair Scheduler) 계열을 씁니다.
"각 작업이 지금까지 CPU를 얼마나 썼는지" 기록해두고 **가장 적게 쓴 쪽**에 넘깁니다.
대화형 작업(적게 쓰고 자주 기다림)이 자연스럽게 먼저 처리되는 효과가 있습니다.

알고리즘 이름을 외우는 것보다, **모든 스케줄러가 응답 시간과 처리량 사이에서
어느 한쪽을 고르고 있다**는 구조를 잡는 게 중요합니다.

## 주니어가 자주 빠지는 함정

### 함정 1 — worker 수를 코어 수와 무관하게 정한다

```python
# 흔한 실수 - 클수록 좋다고 생각
# gunicorn --workers 64

# 권장 - 작업 성격에 따라 출발점이 다르다
import multiprocessing
cores = multiprocessing.cpu_count()

# CPU-bound: 코어 수 근처. 더 늘리면 전환 비용만 늘어남
workers = cores

# IO-bound: 대기 시간이 길어 더 늘려도 이득
workers = cores * 2 + 1
```

핵심 기준은 하나입니다.

> 이 서버는 **CPU를 쓰느라** 바쁜가, **기다리느라** 바쁜가.

CPU를 쓰느라 바쁘면 코어 수를 넘기는 순간부터 전환 비용만 늘어납니다.
기다리느라 바쁘면 대기 중에는 CPU를 놓으므로 더 띄워도 됩니다.

이번 주 수요일·금요일에 이 값을 실제로 정해봅니다.

### 함정 2 — 바쁜 대기(busy waiting)를 한다

```python
# 흔한 실수 - 기다리는 동안 CPU를 계속 붙잡는다
while not task_done:
    pass          # 코어 하나를 100%로 태운다

# 조금 나음 - 하지만 여전히 폴링
import time
while not task_done:
    time.sleep(0.01)

# 권장 - 이벤트로 대기. 커널이 깨워줄 때까지 CPU를 놓는다
import threading

done = threading.Event()
done.wait()       # 대기 중에는 스케줄러가 이 스레드를 아예 건너뜀
```

첫 번째 코드는 아무 일도 안 하면서 코어 하나를 다 씁니다.
그 코어를 쓸 수 있었던 다른 작업들이 전부 밀립니다.

`Event.wait()`을 쓰면 이 스레드는 `waiting` 상태로 들어가서
스케줄러의 후보 목록에서 빠집니다. 깨울 때가 되면 커널이 알려줍니다.

### 함정 3 — 짧은 주기 폴링을 여기저기 깔아둔다

```python
# 흔한 실수 - 1ms마다 DB를 확인
while True:
    status = check_device_status()
    time.sleep(0.001)

# 권장 - 주기를 늘리거나, 이벤트 기반으로 바꾼다
while True:
    status = check_device_status()
    time.sleep(1)          # 요구사항이 허용하는 만큼 길게
```

`sleep(0.001)`은 초당 1,000번 깨어난다는 뜻이고, 깨어날 때마다 컨텍스트 스위칭이 일어납니다.
이런 루프가 여러 개 돌면 CPU가 실제 일보다 전환에 시간을 더 씁니다.

폴링 주기는 **정확도가 아니라 요구사항**으로 정합니다.
"1초 안에만 감지하면 된다"면 `sleep(1)`이 맞습니다.

### 함정 4 — 비용이 있다는 걸 숫자로 확인해본 적이 없다

리눅스에서는 바로 볼 수 있습니다.

```bash
vmstat 1
# cs 열이 초당 컨텍스트 스위칭 횟수

pidstat -w -p <PID> 1
# cswch/s   자발적 전환 (IO 대기 등)
# nvcswch/s 비자발적 전환 (타임 슬라이스 만료)
```

`nvcswch/s`가 유난히 높으면 **실행 가능한 작업이 코어 수보다 지나치게 많다**는 신호입니다.
worker를 줄여볼 근거가 됩니다.

숫자를 한 번 보고 나면 이 주제가 추상적인 이론에서 튜닝 가능한 손잡이로 바뀝니다.

## 트레이드오프

```
타임 슬라이스를 짧게 잡으면
  얻는 것: 반응성 향상. 모든 작업이 빨리 한 번씩 CPU를 잡음
  잃는 것: 전환 횟수 증가로 전체 처리량 감소

타임 슬라이스를 길게 잡으면
  얻는 것: 전환 비용 감소, 캐시를 오래 활용해 처리량 향상
  잃는 것: 짧은 작업이 긴 작업 뒤에서 오래 기다림

스레드/프로세스를 많이 띄우면
  얻는 것: IO 대기 시간을 다른 일로 메울 수 있음
  잃는 것: 전환 비용, 메모리 사용량, 캐시 효율 저하
  손해로 뒤집히는 지점: CPU-bound 작업에서 코어 수를 넘어설 때
```

여기서 한 가지 관점이 나옵니다.
**컨텍스트 스위칭을 줄이는 가장 확실한 방법은 스레드를 안 늘리는 것입니다.**

스레드 하나로 여러 요청을 처리하는 방식, 즉 이벤트 루프가 그 답입니다.
커널이 개입하는 전환 대신 애플리케이션이 직접 작업을 번갈아 처리하므로 훨씬 쌉니다.
FastAPI의 `async`가 정확히 이 전략입니다. 4주차 월요일에 이어집니다.

다만 이것도 만능은 아닙니다. `async` 함수 안에서 CPU를 오래 잡으면
이벤트 루프 전체가 멈춥니다. 스케줄러가 강제로 뺏어주지 않기 때문입니다.
선점형 스케줄링을 포기한 대가입니다.

## 연결되는 CS 지식

- **프로세스와 스레드** — 1주차 월요일 내용의 비용 측면입니다. "가볍다/무겁다"의 실체가 오늘 내용입니다.
- **가상 메모리와 TLB** — 프로세스 전환이 왜 비싼지, TLB 무효화가 무엇인지 설명해 줍니다. (3주차 월요일 주제)
- **동기/비동기, 블로킹/논블로킹** — 커널 전환을 피하는 대안으로서의 이벤트 루프입니다. (4주차 월요일 주제)
- **락과 데드락** — 락을 잡은 스레드가 전환되어버리면 다른 스레드들이 전부 대기합니다. 전환 타이밍과 동기화가 만나는 지점입니다.
- **인터럽트와 시스템 콜** — 전환을 촉발하는 실제 방아쇠입니다.

## 다음 행동 (금요일 실험용 스크립트 예고)

이번 주 금요일 실험은 이 형태가 될 예정입니다.

```python
# 스레드 수를 1, 2, 4, 8, 16, 64로 바꿔가며
# (1) CPU-bound 작업  (2) IO-bound 작업
# 두 가지의 총 실행 시간을 각각 측정한다
```

CPU-bound는 어느 지점부터 **더 느려지고**, IO-bound는 계속 빨라지다가 평평해집니다.
그 꺾이는 지점이 오늘 배운 전환 비용이 이득을 넘어서는 순간입니다.
동시에 `vmstat 1`을 띄워두면 `cs` 수치가 같이 올라가는 것을 볼 수 있습니다.

1주차 금요일에 못 한 프로세스/스레드 ID 확인도 이 스크립트에 함께 넣으면
두 주치 내용을 한 번에 회수할 수 있습니다.
